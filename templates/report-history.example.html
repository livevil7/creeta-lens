05 / 08 · KEY DECISIONS

왜 이렇게 설계했나

일회성 작업에서는 정확도보다 투명성, 알고리즘 정교화보다 명시적 처리.

01

Jaccard 유사도

bag-of-words 기반 단순/투명 알고리즘. 왜 그 점수가 나왔는지 즉시 추적 가능. 정확도보다 transparency가 중요한 one-off 작업이라 채택.

02

임계값 0.146

0.20에서 시작 → stemming 추가로 35 클러스터 → 0.146까지 lower bound 확장. dry-run 검토 끝에 자동 적용 가능함 확인.

03

Cluster fanout 동기화

EN-primary가 매칭되면 ko/ja/zh hash variant도 동일 날짜로. i18n 클러스터 정합성을 우선.

04

9개 false positive 명시 제외

"Seoul Pilgrimage Tour"가 K-POP 클러스터의 magnet으로 작동. 알고리즘 개선 대신 manual exclude list가 더 효율적.

05

-en suffix strip

마이그레이션된 EN-only 글의 -en suffix로 fanout 글과 그룹핑 안 되던 문제. cluster_key 산정 시 suffix 제거.

06

noon-UTC 타임스탬프

YYYY-MM-DDT12:00:00.000Z 사용. 타임존이 음수 shift될 때 발생하는 날짜 -1 이슈 회피.

06 / 08 · VALIDATION

어떻게 믿을 수 있나

live 데이터 변경 작업. 검증 없이 적용하지 않음. 4단계 안전망이 0 에러를 만든 이유.

live API를 건드리기 전, 모든 변경을 사람이 읽을 수 있는 형태로 검토.

  1. Dry-run 검증

    apply_dates.py --threshold 0.146를 --apply 없이 실행. 172 PUT 요청 미리 출력 후 4-language fanout이 모두 포함되는지 확인.

  2. 점진적 임계값 튜닝

    처음 0.20 → 33 clusters. stemming 추가 → 35. 0.146까지 낮춰가며 0.10–0.146 범위의 false positive 분포를 직접 검토.

  3. 라이브 직접 verification

    apply 후 Ghost Admin API로 3개 post 직접 GET — budget-korea-travel-en → 2023-12-28, april-weather-korea-ja → 2026-03-20 (fanout sync 확인), jeju-restaurants → 2024-01-22 (cluster anchor).

  4. 자동 audit trail

    apply_log.jsonl의 172줄이 모든 PUT의 (post_id, old_published_at, new_published_at, status=ok)을 기록. 역방향 PUT으로 복구 가능.
