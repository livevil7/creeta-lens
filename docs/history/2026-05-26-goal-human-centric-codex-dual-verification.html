05 / 08 · KEY DECISIONS

왜 이렇게 설계했나

사람 중심 분리는 사용자 명시 요청, 더블 검증 형태는 비용·충돌 trade-off 로 선택.

01

Goal=사람 언어, 검증=기계 언어

사용자 명시 요청("무슨 함수가 어쩌고 하면 내가 알아듣겠어?"). 기술 토큰은 목표 문장에서 reject → ✅검증 표로 이동. "사람 목표→검증 ≥1행" 매핑이 곧 게이트.

02

더블 검증 = 항상 (trivial만 skip)

비용·속도보다 안전망 우선(사용자 선택). trivial·비-코드 skip, Codex 부재/실패는 graceful degrade.

03

/cc = Claude 구현 → Codex 리뷰 게이트

독립 구현 후 병합(머지 충돌·비용 큼) 대신 리뷰 루프. Supervisor + Codex 둘 다 PASS 여야 진행.

04

분기는 Claude 가 근거와 함께 결정

객관 판정 불가한 분기는 trade-off 근거와 함께 선택하고 🔀 듀얼 합성 섹션에 기록 — 사용자가 승인 게이트에서 확인.

05

plan-manager.js 전면 동기화

런타임은 SKILL.md 기반(코드 생성기는 백업)이지만 백업·extractGoal·8-lang dict 까지 신구조로 일치시켜 latent drift 제거.

06

v3.8.0 별도 릴리스 안 함

미커밋 상태에서 v3.9.0 작업이 이어져 한 커밋·태그로 묶음. CHANGELOG 는 [3.8.0]·[3.9.0] 항목 분리 유지.

06 / 08 · VALIDATION

어떻게 믿을 수 있나

코드 생성기는 실측, 릴리스는 체인 검증, 설치는 실제 플러그인 install 까지 확인.

텍스트 검토가 아니라 실제 node 실행·릴리스 명령·설치 검증으로 증명.

  1. plan-manager.js 실측

    node -e 로 generatePlanContent(ko) 가 🎯 목표(plain bullet)+✅검증(종류 칼럼)+🔀 듀얼 합성 생성 확인. validatePlanStructure = {valid:true}, extractGoal 왕복(사람 목표→successCriteria) 확인.

  2. 레거시 호환

    옛 체크박스 구조(deliverables + 성공기준) 문서도 extractGoal 이 그대로 파싱. verification 미제공 시 outcomes 로 manual 행 폴백.

  3. 릴리스 체인

    bump-version.sh 3.9.0 (11/11 파일) → commit b27b2a6 + tag v3.9.0 + push(master+태그). 옛 태그 충돌(v1.9.0/v2.0.0)은 릴리스와 무관.

  4. /lens-upgrade 실측

    마켓플레이스 v3.9.0 감지 → claude plugin install lens@CreetaCorp → 검증: registry 1 entry = v3.9.0, claude plugin list 확인.

  5. Karpathy 규칙 보존

    새 3.9.0 캐시의 c/cc/cp SKILL.md 전부 MUST FOLLOW 마커 포함 직접 grep 확인 (검증 스크립트는 stale 이라 우회).
