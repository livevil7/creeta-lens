03 / 08 · PROBLEM

"진짜로 작동하는가"를 증명할 진입점이 없었다

/cc는 만들면서 검증한다. 하지만 이미 만들어진 임의의 산출물을 출처와 무관하게 독립적으로, 실제 실행으로 증명·수복할 전용 진입점은 비어 있었다.

Before

한 명의 "되는 것 같다"

단일 시각의 표면 점검에 의존. 빈/에러 상태에서 깨지는 엣지·회귀를 놓치고, 검증 못 끝낸 채 "완료" 오통지 위험.

"무슨 수를 써서라도 검증"이 배포·DB·삭제 같은 파괴적 변경으로 번질 여지도 있었다.

After

4 렌즈가 깨려고 시도

앱을 실제로 띄워(Playwright) 클릭·관측 → 4 렌즈가 각자 적대적으로 반박 → 빈/에러 상태에서 발견 → 최소 수복 → 재검증.

결과는 "전부 통과(증거 첨부)" 또는 verified=false + 막힌 지점 + 다음 액션. read-only 우선으로 안전.

04 / 08 · PIPELINE

핵심 검증 루프

증거를 모으고, 깨고, 고치고, 다시 증명한다. 안 되면 정직하게 멈춘다.

1

증거 수집

앱을 실제 실행(Playwright 등)해 클릭·관측. read-only 우선으로 산출물의 실제 동작을 관측한다.

2

4 렌즈 반박

기능·엣지·회귀·UX 4 렌즈가 각자 깨려고 시도. 빈/에러 상태에서 깨지는 지점을 적대적으로 찾는다.

3

최소 수복

실패 축만 surgical 하게 수복. pass한 축은 freeze. 5회+예산+전략전환+승인 cap으로 무한루프 방지.

4

재검증 → 증거리포트

blocking refute 0이면 증거와 함께 "작동 확인". 1+ 이면 verified=false + blocking + 다음 액션.

05 / 08 · KEY DECISIONS

왜 이렇게 설계했나

Codex 교차 협의(S4) 반영. 중복 가드 · 안전 우선 · 정직한 종료가 핵심.

01

출처 불문 standalone 감사

/cc와 중복 리스크가 커서 경계를 한 문장으로 차별화 — "이미 만들어진 것을 적대적으로 독립 감사". 같은 작업이면 /cc 권유(다운그레이드 가드).

02

read-only 우선 · 파괴적 차단

"무슨 수를 써서라도"는 read-only 검증까지. 배포·DB migration·대량삭제·외부 결제/메일은 dry-run 또는 승인 없이 금지 (Codex critical).

03

만장일치 게이트

4 렌즈 중 blocking refute가 1개라도 있으면 done 차단. 과반이 아닌 만장일치로 "되는 것 같다"의 통과를 막는다.

04

정직한 종료

못 끝내면 done 금지. verified=false + blocking + 다음 액션으로 마감해 "완료" 오통지를 차단.

05

무한루프 방지 cap

5회 + 예산 + 동일 실패 2회 시 전략 전환 + 3회 승인 cap. 무한 수복 루프(R3)를 차단.

06

Surgical 무수정 원칙

pass한 검증 축은 freeze, 실패 축만 수복. /cc·/cp는 5분 규칙 1줄 외 손대지 않음.
