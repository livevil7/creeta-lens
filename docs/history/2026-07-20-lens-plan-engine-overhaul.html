03 / 08 · PROBLEM

왜 했나 — 규칙이 코드가 아니면 사라진다

Before

계획서에 "무엇을 만드는지"가 빠져 관리자가 승인/반려를 판단할 근거가 부족했다. 결론만 있고 선택의 근거가 없었다. 얕은 계획서도 실행이 그냥 시작됐다. 단순 업무가 최상위 모델을 먹었고, 어떤 모델이 몇 번 쓰였는지 알 수 없었다. /cs 는 기본 브랜치에 직접 밀어 넣었다.

After

비목표·검토된 대안·DO NOT CHANGE·리스크 레지스터·미해결 질문이 필수가 됐다. 필수 항목이 비면 /c·/cc 가 실행을 거부한다. 모든 spawn 이 모델을 명시하고 훅이 기록한다. /cs 는 전부 PR 로 남는다. 계획 스킬은 /cp 하나 · 등급 3개.

핵심 통찰

검사를 작성 시점이 아니라 실행 시점에 뒀다

작성 시점 검사는 우회 경로가 많다 — 다른 쓰기 경로, 파일 없이 응답 본문으로만 낸 계획, 외부에서 수정된 문서, 예전 버전으로 만들어진 문서. 반면 실행 진입은 우회할 수 없다. 그래서 레거시 문서까지 자동 커버되고 소급 정리가 불필요해진다.

04 / 08 · HOW IT WORKS

4개 패키지

1

모델 배분 통제

상속 폐기(모든 spawn 이 명시) · 연쇄 승격 폐기(위험도 기반) · TOP 상한(/cc 3 · /ccp 1 · /cp deep 2) · fan-out 조사 중간 티어 고정 · hooks/pre-tool-task.js + lib/agent-tracker.js 계측 신설.
2

골격 + 실행 진입 게이트

2A 골격(필수 섹션 5종 + 필수7/조건부부록 + 위험도 등급 + 예약어 3개 + 양방향 가드) · 2B 게이트(필수 섹션 코드 검사 · 차단 질문 0 · 단계↔검증 연결 · 라벨↔내용 일치) · 2C /cpp 폐지. validatePlanStructure 를 현행 골격으로 갱신하고 실제 배선했다 — 그전까지 런타임 호출자가 0개였다.
3

/cs PR-only

기본 브랜치 직접 push 폐지. 변경을 sync/<date>-<time> 브랜치로 옮겨 PR 로 제안. 커밋 전에 브랜치를 만드는 순서가 핵심 — 기본 브랜치에 먼저 커밋하면 비교할 변경이 없어 PR 자체가 불가능하다. fail-closed.
4

릴리즈

CHANGELOG·CLAUDE.md 작성, bump-version.sh 를 12파일로 정정(skills/cpp 삭제 반영), v3.25.0 13/13 반영 확인.
되먹임 고리 신설

계획서에 적고 넘기지 않으면 그 판단은 버려진다

핸드오프에 NON_GOALS·DO_NOT_CHANGE·REJECTED_ALTERNATIVES·BLOCKING_QUESTIONS·GRADE 를 추가하고 worker 프롬프트에 실제 주입했다. DO NOT CHANGE 가 없으면 worker 가 무관한 코드를 "개선"하고, 비목표가 없으면 범위를 넘고, 기각된 대안이 없으면 이미 버린 접근을 다시 시도한다. 여기에 편차 기록과 실행 지표를 더해 /cp → /cc → ??? 로 끊겨 있던 고리를 닫았다.

05 / 08 · DECISIONS

주요 결정

등급은 분량이 아니라 위험도로

줄 수·페이지 수로 등급을 정하면 길이가 품질의 대리값이 되어 내용 없는 문서가 길이만으로 통과한다. 기준은 "되돌리기 얼마나 어려운가".

/cs auto-merge → PR-only 로 축소

당초 사용자 선택은 "PR + 자동 머지"였으나 Codex 협의에서 "auto-merge 가 즉시 실행되면 PR 은 검토 단계가 아니라 기록용 포장" 이라는 반박이 나와 사용자 재확인 후 축소했다. auto-merge 는 비목표로 분리.

모델 상속 폐기 — 명시하면 기록되고, 기록되면 통제된다

지정을 생략하면 훅이 실제 실행 모델을 관측할 수 없어(tool_input.model = undefined) 계측에 구멍이 생기고, 세션이 최상위 모델일 때 모든 Hard 역할이 자동으로 최상위를 먹었다(실측된 과소비 원인).

연쇄 승격 폐기 — 기준을 티어 대칭에서 위험도로

종전엔 TOP worker 가 하나라도 있으면 Supervisor·QA 도 TOP 이었다. Hard 1개 + Easy 3개 실행에서도 최상위 모델 2개가 추가로 붙었다. 리뷰 깊이가 필요한 것은 "worker 가 똑똑했을 때"가 아니라 "틀렸을 때 손해가 클 때" 다.

미해결 질문은 "차단만 0"

전량 0 을 기계적으로 강제하면 모델이 불확실성을 드러내는 대신 임의 가정을 확정처럼 기록한다 — 질문 은폐를 유도하는 역효과다. 비차단 질문은 가정·확인시점과 함께 남기게 했다.

기각 2건 — 반박이 성립했다

deep 본문 분리(deep.md): 파일 비대화 방지 목적이었으나 정책은 인라인에 남겨야 하므로 오히려 커진다는 반박. 통합으로 중복이 소멸해(−154줄) 애초에 문제가 아니었다. /cpp 통합 순서: 검증 2건이 "품질 문제 해결 전 인터페이스 변경"이라며 보류를 권고 → 폐지는 진행하되 골격 통일 이후로 순서를 재배치해 위험을 해소.
