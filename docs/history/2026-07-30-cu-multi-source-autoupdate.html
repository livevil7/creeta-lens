03 / 08 · PROBLEM

왜 했나 — 표가 신뢰를 잃은 상태였다

사용자 지적 4가지가 모두 실측으로 확인됐다.

Before

표에 9~10줄. winget 143개 설치 중 19개, npm 8개 중 6개가 낡았는데 한 건도 안 보임. VS Code 확장 40여 개는 존재조차 목록에 없음. 업데이트가 있으면 매번 골라달라고 물음. agentmemory 는 최신인데 ⚠️, context7 은 ❓.

After

소스 6종 34항목이 한 표에. 아무것도 선택하지 않았는데 안전한 9건이 이미 최신. 손대지 않은 17건은 사유와 명령이 함께. 플러그인 6건 전부 버전 표시 정확.

근본 원인

못 찾은 게 아니라 찾지 않았다

cu.py 가 도구 이름을 손으로 적어둔 함수 3개(claude·codex·gh)를 부르는 구조라, 목록에 없는 도구는 아무리 낡아도 영원히 안 보였다. CLI 하나 추가에 전용 함수 하나가 필요했다.

오탐 원인

성질이 다른 두 값을 비교했다

대부분의 마켓플레이스 manifest 에 version 필드가 없어 fallback 으로 저장소 HEAD SHA 를 "최신"으로 잡고, 이를 설치된 semver 와 비교했다 → 항상 불일치 = 무조건 "업데이트 있음".

04 / 08 · HOW IT WORKS

동작 — 소스가 열거하고, 위험도가 결정한다

질문은 없애고 판단은 정책으로 남겼다.

1

소스 열거

winget · npm-global · vscode-ext · claude-plugin · cli-special · pip-global · brew. 패키지 매니저가 자기 목록을 낸다. 없는 소스는 조용히 빠지고, 실패한 소스는 반드시 보고된다.
2

위험도 부여

auto(무확인) / hold(/cu all 로만) / never(어느 모드에도 제외). 정책은 파일 상단 상수 한 블록에 집결 — 흩어지면 "왜 hold 인가"를 추적할 수 없다.
3

실행 전 예고

"auto N건을 확인 없이 실행합니다 / hold M건 · never K건은 건드리지 않습니다" 를 먼저 출력. 사후 보고만 있으면 사용자가 게이트 제거를 모른 채 실행을 겪는다.
4

순차 실행 + 경계 강제

auto 항목을 하나씩. cmd_upgrade 진입부가 never 를 코드로 거부(exit 3). 호출자의 필터링을 믿지 않는다.
5

사후 재스캔 1회

사전 스냅샷(scan --snapshot)과 대조해 실제로 무엇이 올라갔는지 확인. 무확인 실행에서 이것이 유일한 검증 수단이다.
6

보류 항목 안내

사유 + 직접 실행 명령. 승격 필요 항목은 PowerShell foreach 루프 한 줄로 묶어 제시 — winget 은 --id 중복을 거부한다.
05 / 08 · DECISIONS

주요 결정

never 3단계 신설 — 데이터 손실 우려 대응

초안은 2단계였고 /cu all 이 hold 전량을 실행했다. 그런데 hold 에 PostgreSQL 이 있어 오타 한 번으로 DB 마이그레이션이 일어난다. "사용자가 all 을 타이핑했으니 승인"이라는 논리는 되돌릴 수 없는 손실을 정당화하지 못한다 → /cu all 로도 닿지 않는 층을 뒀다. (Pre-mortem P1)

never 를 문서가 아니라 코드로 강제 — 이번 작업의 최대 수정

upgrade_targets() 가 never 를 제외하도록 설계했지만 실행 흐름은 그 함수를 경유하지 않는다(에이전트가 스캔 JSON 을 읽고 cu.sh upgrade <id> 를 개별 호출). 테스트에서만 불리는 죽은 방어선이었다. Codex 와 Supervisor 가 독립적으로 같은 지점을 지목해 발견됐다.

소스 단위 열거로 전환

CLI 하나당 함수 하나 쓰는 구조를 버렸다. 패키지 매니저가 이미 전체 목록을 안다. 결과적으로 cli:codex·cli:gh 전용 스캐너가 삭제됐다 — 각각 npm·winget 이 잡는다.

판단 불가는 항상 보수적으로

버전 파싱 실패 → hold. 형태 불일치(semver↔SHA) → None, 절대 True 금지. 미지의 mode 값 → hold 해제 안 함(화이트리스트). 애매함이 폭발 반경을 넓히면 안 된다.

위험도를 설정 파일로 빼지 않았다 · LLM 에 위임하지 않았다

설정 파일은 요청하지 않은 유연성이고 없을 때·깨졌을 때 처리가 붙는다. LLM 위임은 실행 정책이 인증·네트워크·모델 변경에 흔들리고 "왜 이게 올라갔나"를 재현할 수 없게 만든다 — 실행 정책은 결정적이어야 한다.

fixture 는 실캡처만, 테스트는 구현보다 먼저

손으로 쓰면 컬럼 폭이 실물과 어긋나 "테스트는 통과하는데 파서는 깨지는" 최악의 조합이 된다. 실제로 이 테스트가 redis ⊂ vcredist 부분 문자열 충돌(VC++ Redist 가 never 로 오분류)을 잡아냈다.

06 / 08 · VALIDATION

검증 — 실행해보지 않으면 못 잡는 것들

더블 게이트 1라운드는 Codex·Supervisor 양쪽 모두 fail 이었다. 결함 14건 전수 수정 후 재검증.

단위 68/68 pass · 실측 auto 9건 업그레이드 · hold 14 · never 3 버전 불변 · Goal 4/4.

  1. never 경계가 코드로 닫혔다

    bash scripts/cu.sh upgrade winget:PostgreSQL.PostgreSQL.18 → 실행 없이 exit 3, PostgreSQL 18.4-1 유지. 가드와 분류기가 같은 정책 상수를 쓰는지 검사하는 단정도 추가 — 두 정책이 갈라지면 테스트가 잡는다.

  2. winget HRESULT 마스킹 함정 (실측으로 당했다)

    Python subprocess 는 32비트 원값(0x8A15002B=2316632107)을 받지만 셸은 하위 1바이트(43)만 보여준다. 셸에서 잰 값을 상수로 쓰면 Python 경로에서 하나도 안 맞는다. 양쪽 인정 + 종료코드 규약(0/1/2/3)으로 사상해 해석 불가한 값이 새어 나가지 않게 했다.

  3. 소스 일시 장애 — 재시도로 통과

    msstore REST API 오류(0x8A15003B)로 winget 5건이 전부 실패했고 같은 명령 재시도로 통과했다. 한 번의 일시 장애로 그날의 자동 갱신이 통째로 날아가지 않도록 재시도 1회를 넣었다.

  4. CJK 표시폭은 가설이 아니었다

    winget 은 표시 폭으로 컬럼을 정렬하므로 한글 이름 행은 문자 인덱스가 어긋난다. 이 머신 출력에 실제로 AVC 인코더 비디오 확장 이 있어 라이브 경로였다 — 실캡처로 보정을 검증했다.

  5. 오탐 2건 · ❓2건 해소

    agentmemory 0.9.28→0.9.28 False, insane-search 0.13.0→0.13.0 False. context7·playwright 는 gitCommitSha 로 SHA 대 SHA 판정 성립.

  6. 그 외 수정된 결함

    upgrade_targets fail-open · 최신 항목 매번 재설치 · /cu scan 이 실제 업그레이드 실행 · 소스 실패 시 "모두 최신" 종료 · 사후 재스캔이 사전 스냅샷 파괴 · winget 실패가 소스를 조용히 삭제 · 비영어 로케일 0건 · 드라이버 복합어 누락 · UAC 무한 대기 · README 계약 불일치 · stderr mojibake.

08 / 08 · WHAT'S NEXT

남은 것 · 되먹임

필요 조치

이 머신에서 아직 활성이 아니다

활성 플러그인 캐시는 lens/3.25.0 이고 그 cu.py 는 구버전이다(계약 함수 0/3). /cu 를 치면 옛 스캐너가 돈다. /lens-upgrade → Claude Code 완전 재시작 필요. 이번 검증은 전부 레포의 scripts/cu.sh 직접 호출로 수행했다.

한계

승격 커버리지 — 19건 중 auto 5건

Git 2.54→2.55 · AWS CLI · Tailscale · WeChat · QMK · Futuremark 6건은 위험해서가 아니라 권한 때문에 hold 로 갔다. 관리자 권한 세션에서는 auto 가 된다.

정상 동작

context7 · playwright 는 재시작 대기

refreshed from source. Restart to apply changes. 재시작 전까지 레지스트리 SHA 가 안 바뀌므로 /cu 가 계속 대기로 표시한다 — 실패가 아니라 정직한 상태.

후속

Mac Mini(brew) 실측

brew 스캐너는 자리를 만들었으나 Windows 에서만 검증했다. lib/install-sync.js 일관성은 조사 결과 충돌 없음으로 판정 — 후속 태스크 불필요.

되먹임 — 계획

파일 단위 충돌을 태스크 분할에 반영해야 한다

T1~T5 를 병렬 태스크로 쪼갰지만 전부 같은 cu.py 를 수정하므로 실제로는 직렬화가 강제됐다. Pre-mortem 이 T3·T4 만 지적했는데 실은 T1~T5 전체가 같은 문제였다.

되먹임 — 실행

mtime 부재는 에이전트 사망 근거가 못 된다

배포 8분 시점에 산출물이 없다는 이유로 "Worker 3개 사망"으로 판단하고 직접 실행 전환을 선언했으나 오판이었다 — 세 Worker 모두 정상 동작(212·294·854초 완료). 대형 계획서를 읽는 동안은 산출물이 없는 것이 정상이며, 생존 판정 기준은 완료 알림이어야 한다.

되돌리기 쉬운 것은 묻지 않고 올린다. 되돌릴 수 없는 것은 코드가 막는다.
