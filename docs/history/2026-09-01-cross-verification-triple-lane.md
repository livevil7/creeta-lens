# 교차검증 타임아웃 근절 + 3중 레인 (v3.36.0)

## ❓ Why — 왜 했나

소유자 보고: *"creeta lens에서 codex를 병렬로 검증하거나 개발할 때 지금 계속 타임아웃이 걸리거나 해서 제대로 활용을 못 하는 케이스가 너무 많은데? 거의 90% 이상으로 타임아웃이 걸리고 있어."*

이게 비싼 이유는 실패의 방향 때문이다. **교차검증은 작업이 클수록 잘 죽었고**, 하드 게이트가 가장 필요한 순간에 정확히 무력화됐다. Lens 는 이 증상을 두 번 겪고 두 번 다 **상한을 올려서** 대응했다(v3.19 → v3.25, 180 → 600초). 두 번 다 틀린 처방이었다는 것이 이번 조사의 결론이다 — 기다리고 있던 것은 추론이 아니었다.

동시에 소유자 요청: *"gork CLI 토큰이 있어, 이것도 병렬로 진행할 때 cp, cc 둘 다에다가 넣을 수 있지 않아? 검증을 3중으로 하게끔 설정."*

## 🎯 목표

1. 교차검증 호출이 **구조적으로** 타임아웃하지 않는다 (상한을 올리는 방식이 아니라 원인 제거).
2. `/cp` 와 `/cc` 의 검증이 **Claude ‖ Codex ‖ Grok 3중**으로 돈다.

## 🔍 What — 원인 (전부 실측)

「codex 가 느리다」로 보이던 것의 대부분은 모델이 아니라 **배관**이었다. 원인은 하나가 아니라 넷이었고, 서로를 가리고 있었다.

### 1. stdin 영구 대기 — 전체의 ≈83%

`codex exec` 와 `grok -p` 는 파이프된 stdin 을 프롬프트에 덧붙인다 (`codex exec --help`: *"If stdin is piped and a prompt is also provided, stdin is appended as a `<stdin>` block"*). Claude Code Bash 도구의 stdin 은 **EOF 가 오지 않는 열린 파이프**라, codex 는 첫 토큰을 내기 전에 — 세션 배너조차 찍기 전에 — 멈춘다.

| stdin | 결과 |
| --- | --- |
| 미차단 (v3.35 까지) | **3/3 상한까지 행 · 산출 0바이트** |
| `</dev/null` | **3/3 성공 · 6–8초** |

세션 누적 12회 중 미차단 성공은 2회(**83% 실패**). 최초 재현은 *100단어·파일탐색 금지* 프롬프트가 **240초 타임아웃·0바이트**였던 것이고, 같은 호출이 수정 후 **19초·323바이트**로 돌아왔다. 입력 크기와 무관했다는 것이 결정적 단서였다.

> 이것이 v3.25 의 오진을 만든 기전이다. 큰 작업일수록 호출 횟수와 대기가 길어 이 증상이 두드러졌고, 그래서 「대규모라 느리다」로 읽혔다. **상한을 600 으로 올려도 `-o` 산출이 0바이트였던 이유**가 바로 이것 — 문서에 "부분 수거는 실제로 거의 안 된다"고 적힌 그 관측의 진짜 원인이다.

### 2. `codex exec review --uncommitted` 의 무제한 탐색

CLI 가 `--uncommitted` 와 `[PROMPT]` 의 **병용을 거부**한다 → 탐색 범위를 지시할 자리 자체가 없다. 실측(이 레포): 300초 동안 레포 전역 `rg`·PowerShell 을 **22회** 돌리고 644KB JSONL 만 남긴 채 판정 실패.

규칙 문서의 *"초과가 반복되면 상한보다 프롬프트를 먼저 의심하라"* 가 정확히 적용되는 상황인데, 이 레시피에는 의심할 프롬프트가 없었다.

### 3. 하네스 상한이 스크립트 상한보다 낮다

Claude Code Bash 도구 기본 상한 **120초**(최대 600). 스크립트가 `--timeout 300` 을 걸어도 도구가 먼저 죽이면 **종료 코드 3 도 부분 출력도 남지 않는다** — 호출자는 degrade 판단조차 못 한다. 그런데 스킬의 한 줄 레시피는 도구 `timeout` 을 언급하지 않았다.

### 4. background 수거 불가

레시피 `OUT="$(mktemp)"; bash …/codex-review.sh --out "$OUT"` 는 경로가 background 셸 안에서만 존재해 Leader 가 결과를 찾을 수 없다. **정작 두 스킬이 지시한 실행 방식이 background 였다.**

부수적으로: `--output-schema` 스키마에 `additionalProperties: false` 가 없어 서버가 400 을 냈다. `exec review` 가 애초에 최종 메시지에 도달하지 못해 드러나지 않았을 뿐, v3.35 까지 이 스키마는 **무효**였다.

## 🛠 How — 처방

| 원인 | 처방 | 실측 |
| --- | --- | --- |
| stdin 대기 | 모든 에이전트 호출에 `</dev/null`, 프롬프트는 `- < FILE` | 240s·0B → **19s·323B** |
| argv 한도 | 프롬프트를 stdin 으로 | 214KB argv `rc 126` → stdin **rc 0·6s** |
| 무제한 탐색 | `exec review` 폐기 → diff 주입 + `codex exec` + `--output-schema` + 탐색 상한 프롬프트 | 300s 판정실패 → **256–329s 정상 verdict** |
| 하네스 상한 | 스킬에 background 또는 명시 `timeout` 의무화 | — |
| 수거 불가 | `.lens/verify/<tag>-<lane>.out` 결정 경로 | — |

**3중 레인**: `scripts/grok-review.sh` 신설(플래그·종료 코드가 `codex-review.sh` 와 동일 — 네 번째 레인은 파일 복사가 절차의 전부) + `scripts/cross-verify.sh` 오케스트레이터가 두 레인을 동시에 띄우고 `LANE`/`FINDING`/`VERDICT` 세 줄로 합쳐 보고. 호출자는 여전히 한 줄이다.

설계에서 지킨 것 셋:
- **죽은 레인은 투표하지 않는다** — 침묵을 pass 로 세면 도구가 깨지는 순간 게이트가 약해진다.
- **종료 코드에 판정을 싣지 않는다** — 0 아닌 종료는 「스크립트가 깨졌다」와 구분되지 않고, 그걸 못 가리는 게이트는 인프라 오류에서 fail-open 한다.
- **레인 출력은 실행 전에 비운다** — 낡은 FAIL 이 새 FAIL 로 읽히는 것은 게이트가 작동하는 것처럼 보여서 가장 나쁜 오답이다.

## ✅ Review — 검증

- `tests/test_cross_verify.sh` **13/13 PASS**. 결함 하나하나에 단언이 붙어 있다(stdin·argv·스키마·read-only·strict 금지·허용목록·종료코드 계약 + 스텁 레인으로 검증한 병합 판정 4종).
- 라이브 3중 실행: `LANE codex status=ok verdict=fail findings=4 elapsed=329s` · `LANE grok status=ok verdict=pass findings=0 elapsed=329s` · `lanes_down=0`.
- **자기검증**: 이 릴리즈의 코드가 새 게이트를 통과하는 과정에서 **자기 결함 9건**이 잡혔다 — argv 한도, 무표시 절단, 프롬프트 인젝션, 심볼릭 링크 역참조(레포 밖 시크릿이 프롬프트에 실림), `unknown` 판정이 pass 로 세지던 것, 낡은 레인 출력 잔존 등. 소유자 지시(2026-08-22) *"그 규칙으로 클로드 못 잡은 버그를 아주 많이 잡았어"* 가 그대로 재현됐다.

## ⚠️ 남은 리스크 (수용)

리뷰 대상 diff 는 원리적으로 신뢰할 수 없는 입력이고, 두 레인 모두 **읽기 도구는 계속 쥔다**. `-s read-only` 는 쓰기를 막을 뿐 읽기 범위를 좁히지 않는다.

- **막았다**: 쓰기·셸 실행(허용목록에 `bash`·`search_replace` 없음), 심볼릭 링크 역참조.
- **남겼다**: 레포 내 파일 읽기. 리뷰어에게서 읽기를 뺏으면 근거를 확인 못 해 *"정보 부족으로 판단 불가"* 만 내놓는 레인이 된다 — 실측으로 확인했고, 그 응답이 high 지적으로 올라가 게이트를 거짓 차단했다.
- **전제**: `/cc` 가 리뷰하는 diff 는 자기 Worker 가 방금 쓴 것이다. 외부 PR 처럼 제3자가 쓴 diff 를 물릴 때는 이 전제가 깨지므로, 그때는 시크릿이 레포 안에 없는지 먼저 확인한다.

## 🔀 Side Effect

- `/cp`·`/cc` 의 codex 호출 지점이 전부 `cross-verify.sh` 로 바뀌었다. 기존 `codex-review.sh` 직접 호출도 계속 동작한다(계약 불변).
- 리뷰 1회 벽시계가 레인 병렬화로 **두 레인 중 느린 쪽**(현재 codex, 256–329초)에 수렴한다 — grok 추가에 따른 추가 대기는 없다.
- 소유자 `~/.codex/config.toml` 은 여전히 `sandbox_mode = danger-full-access` 다. Lens 호출만 `-s read-only` 로 좁혔고, 다른 codex 사용처는 그대로다.
