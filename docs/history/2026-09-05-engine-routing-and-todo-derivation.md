# 엔진 배분 + 실행 Todo 파생 (v3.38.0)

## ❓ Why — 왜 했나

소유자 지시 두 건 (2026-09-05):

> *"lens 의 cc 기능에 모델 토큰을 최대한 효율적으로 개발을 실행하는 걸 좀 더 추가하면 좋겠는데, fable 5.1 을 아무 데나 쓰면 너무 토큰 소모량이 크고, codex 도 astra 가 나와서 똑똑하거든, grok 은 빠르고 효율적으로 하니. `/cc` 로 작업을 할 때 이걸 병렬로 효율적으로 task 를 실행할 수 있게 배분하는 규칙을 넣어라."*
>
> *"그리고 `/cp` 를 할 때 todo list 는 제대로 안 만드는 거 같은데 그것도 제대로 만들게 하고."*

두 지시는 별개로 보이지만 같은 실패 형태다 — **아무도 세지 않는 것은 조용히 줄어든다.** 하나는 비용이 줄지 않았고, 하나는 목록이 줄었다.

## 🔍 What — 무엇이 문제였나 (실측)

### 1. `/cc` 는 서브태스크를 한 종류로만 처리했다

v3.37 까지 `/cc` 의 실행 단위는 `Agent` 서브에이전트 **하나뿐**이었다. §4.1 모델 사다리는 *Claude 안에서 어느 모델을 쓸지*만 정했고, **애초에 Claude 안에서 해야 하는 일인가**는 아무 데서도 묻지 않았다. 그래서 파일을 읽기만 하는 조사 서브태스크까지 전부 **유일한 종량 자원**으로 샀다.

이 기계에는 이미 두 엔진이 설치·인증돼 있었다:

| 엔진 | 실측 | 과금 |
|---|---|---|
| Codex | `~/.codex/models_cache.json` priority 1 = **`gpt-6-astra`** (visibility list, supported_in_api) | ChatGPT 구독 — 호출당 0 |
| Grok Build CLI | `grok 1.0.5 (5115b46bc9)`, `~/.grok/auth.json` 유효 | 구독 — 호출당 0 |

그런데 `/cc` 는 이 둘을 **Phase 4.5 리뷰 게이트에서만** 썼다. 실행에는 한 번도 안 썼다.

### 2. `/cp` Phase 4 는 산문 15줄이었다

종전 Phase 4 전문은 *"Goal 의 성공 기준 + Plan A 의 체크리스트로 TodoWrite 항목을 생성합니다"* 였다. 개수를 세는 코드가 없고, 계획서와 대조하는 게이트가 없고, 승인 화면에 개수를 보여 주는 줄도 없었다.

이 레포의 자체 판정 규칙(harness-rules §6)이 이 결과를 예측한다 — **눈에 보이는 산출물은 산문 지시로도 이행되지만, 눈에 안 보이는 자기절제는 코드가 필요하다.** v3.32 커버리지 원장은 *계획서 안*의 누락을 기계로 잡게 만들었는데, **계획서와 실행 목록 사이**는 여전히 산문이었다. 인벤토리 44행짜리 문서(`2026-08-22-harness-audit-reduction.md`)가 Todo 몇 개로 줄어드 는지 아무도 볼 수 없었다.

## 🛠 How — 무엇을 넣었나

### A. 엔진 배분 (`/cc` + harness-rules §4.9 = SoT)

**난이도로 모델을 고르기 전에 엔진부터 고른다.** 판정은 능력이 아니라 **필요**다:

1. 파일을 쓰는가 / Skill 이 필요한가 / MCP 도구가 필요한가 / 세션 컨텍스트·게이트 원장을 봐야 하는가 → **Claude 레인**. 그 다음에야 사다리로 모델을 고른다.
2. 아니면(읽고 답하는 일이면) 외부 레인. 깊은 추론 = Codex, 넓고 빠른 조회 = Grok.
3. 모호하면 Grok 부터 — 십수 초, 틀려도 손해 0.

**"Claude 도 할 수 있다"는 Claude 레인에 남길 이유가 아니다. 같은 품질이면 정액이 이긴다.**

### B. `scripts/delegate.sh` — 배관은 한 줄

`cross-verify.sh` 의 형제다. 같은 교훈 위에 서 있다 — v3.34 는 인라인 40줄 레시피가 `/cc` 안에서 **0회** 쓰였음을 실측했다. 안 쓰이는 이유는 도구가 아니라 매번 다시 타이핑해야 하는 배관이었다.

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/delegate.sh" \
  --task recon:grok:.lens/delegate/recon.txt \
  --task audit:codex:.lens/delegate/audit.txt \
  --timeout 420
```

`--task` 를 붙인 만큼 **동시에** 돌고 벽시계는 합이 아니라 max(엔진). 출력은 `TASK`/`DISPATCH` 두 줄 종류뿐. 기존 `codex-review.sh`·`grok-review.sh` 의 `--mode prompt` 를 그대로 태우므로 v3.34~3.36 이 산 불변식(stdin `</dev/null`, argv 대신 파일, 읽기 전용 posture)을 다시 사지 않는다.

**실엔진 실측 (2026-09-05)**: 두 엔진 동시 디스패치 **35초**, 둘 다 정확한 답. Grok 은 이번에 새로 만든 `delegate.sh` 를 포함해 `scripts/*.sh` 8개 역할을 정확히 나열했고, Codex 는 `cross-verify.sh` 의 timeout 레인 처리를 3줄로 정확히 요약했다.

### C. Phase 1.35 정찰 위임 — 가장 비싼 독자는 Leader 다

3.0 의 *"fan-out 전 인라인 정찰"* 과 승인표의 `건드릴 파일` 칸은 누군가 레포를 읽어야 채워진다. 그런데 **Leader 는 세션 모델(대개 최상위)이라 레포를 읽는 가장 비싼 방법**이다. 기본값을 Grok 위임으로 바꿨다.

이 산출물은 v3.34 가 *"Worker 템플릿에 `관련 파일:` 슬롯이 있는데 그 슬롯을 무엇으로 채울지 정의한 문장이 어디에도 없어 배관이 끊겨 있다"* 고 지적한 그 슬롯을 채운다. 단 **경로 존재는 Leader 가 직접 확인한다** — 외부 엔진 산출물은 근거지 판정이 아니다.

### D. `deriveTodoItems()` — 목록은 판단이 아니라 파생이다

`lib/plan-manager.js`. 계획서가 이미 세 번 결정해 놓은 것을 되읽을 뿐이다:

| 원천 | 레벨 | 규칙 |
|---|---|---|
| 🎯 What 성공 기준 | Goal | `pending` 유지, QA 만 닫는다 |
| 📋 인벤토리 `포함` 행 | execution | **전건. 압축·병합 금지** |
| 🛠 Plan A `#### 단계` | execution | 전건 |

`/cp` Phase 4 는 이제 이걸 돌리고 출력이 그대로 TodoWrite 입력이다. Phase 5.0 게이트 9 가 `valid` 를 검사하고 승인 화면에 `📝 실행 Todo: N개 (성공기준 g + 인벤토리 i + 단계 s)` 를 찍는다. **표시가 게이트인 이유는 커버리지 게이트와 같다** — 등록 여부는 검사할 수 없지만, 개수가 승인 화면에 보이면 사용자가 "3개?" 를 즉시 잡는다.

표 파서 `readInventoryTable()` 을 커버리지 게이트에서 분리해 둘이 공유한다 — 같은 표를 두 번 파싱하면 칼럼 별칭이 바뀌는 순간 드리프트한다.

### E. TOP(`fable`) 상한 `/cc` 3 → 2

근거는 예산이 아니라 **구성**이다. 읽기가 정액 엔진으로 빠지면 Claude 레인에는 쓰기와 판단만 남는다 — 그 상태에서 한 실행에 TOP 이 세 자리나 필요하다면 분해가 잘못된 것이지 상한이 모자란 것이 아니다. TOP 을 쓴 역할은 **승인표에 사유 한 줄**을 남긴다.

## ⚖️ 감수한 trade-off

**외부 레인은 읽기 전용이다. 쓰기 위임은 넣지 않았다.**

Codex 가 코드를 쓰면 Codex 는 Phase 4.5 에서 **자기가 쓴 코드의 독립 리뷰어일 수 없다** — 3중 게이트가 조용히 2중이 된다. 소유자 지시(2026-08-22): *"그 규칙으로 클로드 못 잡은 버그를 아주 많이 잡았어."* 게다가 외부 쓰기는 Lens 의 어떤 계측도 관측하지 못한다 — PreToolUse 게이트·agent tracker·게이트 원장이 전부 밖이다.

절감폭은 그만큼 줄지만, **절감은 읽기에서만 취한다.** 한 번의 /cc 에서 Claude 워커가 쓰는 토큰의 대부분이 읽기라는 것이 이 선택의 근거다.

### 교차검증이 잡은 것 (이번 변경 자체를 게이트에 태웠다)

**Codex 레인 1차 판정 `fail`, 지적 1건 — 실제 결함이었다:**

> *"`scripts/delegate.sh` — 동일 ID·엔진의 `--task` 를 중복 허용하면서 같은 출력 경로를 배정한다. 병렬 작업들이 서로의 산출물을 덮어쓰고도 모두 ok 로 보고되어, 서로 다른 요청에 같은 결과가 전달될 수 있다."*

수정: `id:engine` 쌍 중복을 파싱 시점에 거부한다. **같은 id 라도 엔진이 다르면 허용**한다 — 그건 "둘 다에게 물어본다"는 정당한 사용이고 파일이 갈린다. 회귀 테스트 2건 추가.

**Grok 레인은 1차 `timeout`** (421초, 0바이트). 규칙대로 **투표하지 않았고 블로킹도 하지 않았다.**

**2차 (상한 900초) — Codex `fail` 1건, 또 진짜 결함이었다:**

> *"`lib/plan-manager.js` — Plan A 를 `###` 제목으로만 찾지만 기존 `generatePlanContent()` 는 `## Plan A` 와 `### Steps` 를 생성한다. 정상 인벤토리를 갖춘 생성 문서도 `steps=[]`·`valid:false` 로 판정되어 새 필수 Todo 게이트에서 Phase 1 로 잘못 회귀한다."*

파서를 `/cp` **마크다운 템플릿**(`### Plan A` + `#### 단계`)에 맞춰 쓰고 **생성기**(`## Plan A` + `### Steps`)를 안 봤다. **Lens 가 스스로 만든 계획서는 전부 두 번째 모양**이므로, 새 게이트가 그것들을 모조리 "단계 없음"으로 되돌렸을 것이다. 수정: 헤딩 깊이 대신 **상대 레벨**로 자른다(`sliceByHeading` — 같은 레벨 이상 헤딩을 만날 때까지). Plan A 매칭은 `startsWith` 로 앵커한다 — 템플릿의 `## 🛠 How — 어떻게 (Plan A / Plan B)` 가 "Plan A" 를 **언급만** 하기 때문이다. 재발 방지 테스트는 **`generatePlanContent()` 를 직접 돌려** 파싱한다(ko/en/de) — 생성기와 파서가 다시 갈라질 수 없다.

**Grok 레인은 2차에서 `unparsable`** — 그런데 **판정은 냈다.** 산출물을 열어 보니 진행 상태 JSON 객체 5개가 앞에 이어 붙어 있어 `grok-review.sh` 의 언랩(첫 `{` ~ 마지막 `}` 그리디 매칭)이 실패했다. 손으로 꺼낸 마지막 객체는 **또 하나의 진짜 결함**이었다:

> *"`deriveTodoItems` 가 성공기준에서 `{…}` 템플릿 잔여를 걸러내지 않아, `/cp` 템플릿의 `- {사람 언어 목표 N}` 이 Goal Todo 로 파생되고 게이트 9 가 `valid:true` 로 통과한다(단계는 같은 잔여를 세지 않음)."*

맞다. `itemsIn`(단계)과 `readInventoryTable`(인벤토리)은 자리표시자를 버렸는데 **성공 기준만 안 버렸다.** `validatePlanStructure` 가 잔여를 잡긴 하지만 그 게이트는 **Phase 5.0** 에서 돈다 — Phase 4 가 이미 목록을 만든 뒤다. 그러면 승인 화면에는 **템플릿 텍스트로 만들어진 건강해 보이는 숫자**가 뜬다. 수정: `isTemplateLeftover` 단일 술어를 셋이 공유하고, 성공 기준이 전부 자리표시자면 별도 사유로 Phase 0 회귀.

**3차 — Codex `fail` 1건, 세 번째 진짜 결함:**

> *"`scripts/delegate.sh` — 중복 검사가 대소문자를 구분하여 `A:grok` 과 `a:grok` 을 모두 허용하지만, Windows 기본 파일시스템에서는 `A-grok.out` 과 `a-grok.out` 이 동일 파일이다."*

1차에서 넣은 중복 방어가 **이 기계에서는 반만 막고 있었다.** 충돌하는 것은 문자열이 아니라 **출력 경로**이므로 키를 소문자로 접어서 비교한다. Grok 3차 판정(`fail: ["review-in-progress"]`)은 **노이즈**다 — 진행 상태를 판정 자리에 흘린 것으로 아래 인접 결함 2번과 같은 뿌리다.

**4차 — Codex `pass`. Grok 은 또 `unparsable` 이었지만 산출물을 열어 보니 진짜 지적 2건이 더 있었다:**

> 1. *"`hooks/pre-tool-task.js:35` — v3.38 이 `/cc` TOP 상한을 3→2 로 바꿨는데 `TOP_CAP` 은 그대로 3 이라, 상한 초과 경고가 4번째 `fable` spawn 에야 뜬다(3번째는 침묵). 이 훅이 바로 '상한이 SKILL.md 산문에만 있으면 안 지킨다'는 이유로 넣은 계측이다."*
> 2. *"`lib/plan-manager.js` — 인벤토리 표가 `{항목}` 자리표시자/빈 행뿐이면 `readInventoryTable` 이 `rows=[]`·`problem=null` 을 돌려 이 검사가 건너뛰어지고, 목표·단계만으로 `valid:true` 가 된다."*

**1번은 이번 변경에서 가장 나쁜 종류의 실수였다.** 상한을 문서 세 곳에서 3→2 로 바꾸고 **그것을 실제로 강제하는 상수를 안 바꿨다** — 이 훅이 존재하는 이유가 정확히 *"상한이 산문에만 있으면 지켜지지 않는다"* 인데, 같은 실수를 한 층 위에서 저지른 것이다. 수정 + **`hooks/pre-tool-task.test.js` 신설**: 훅의 `TOP_CAP` 을 `harness-rules` §4.1 과 `/cc` SKILL.md 표기에 **핀으로 묶는다**. 숫자가 한 곳에서만 움직이면 테스트가 깨진다.

2번도 맞다. 목표·단계는 잔여만 남으면 파생 실패인데 **인벤토리만 빠져나갔다** — 필터가 rows 를 먼저 비워서 "남은 게 있나" 검사가 통째로 건너뛰어졌다. 세 원천 모두 실제 항목을 최소 1개 내야 한다로 통일했다.

**5차 — Codex `fail` 1건 (Grok 판정은 다시 진행 상태 노이즈):**

> *"Plan A 가 같은 깊이의 `### Step 1`·`### Step 2` 로 나뉘면 첫 제목만 단계 블록으로 선택해 두 번째 이후 체크리스트를 누락한다. 재현 결과 단계 2개 중 1개만 반환하면서 `valid:true` 여서, 불완전한 실행 Todo 가 필수 게이트를 통과한다."*

누락이 조용하다는 것이 문제다 — 목록이 짧아지는데 `valid:true` 라 아무도 모른다. 이건 이번 작업이 없애려던 실패 모드 그 자체다. `sliceByHeading` 에 `{ all: true }` 를 더해 **형제 단계 블록을 전부** 모으고, 블록을 닫은 헤딩에서 재개해 다음 형제를 놓치지 않는다.

**6차 — Codex `fail` 1건 (Grok 은 처음으로 깨끗한 `pass`). 5차 수정의 후속 결함이었다:**

> *"모든 단계 블록을 합친 뒤 체크박스가 하나라도 있으면 번호·일반 목록을 전부 버린다. `Step 1` 에 체크박스, `Step 2` 에 번호 목록을 쓰면 두 번째 단계가 Todo 에서 누락되는데도 `valid:true` 로 필수 게이트를 통과한다."*

`itemsIn` 의 "체크박스가 있으면 그것만" 휴리스틱은 **한 블록 안에서** 맞는 규칙인데, 5차 수정이 블록을 합친 뒤에 적용해 버렸다. 블록을 합치지 말고 **블록마다 뽑아서 잇는다**(`sliceHeadingBlocks` 가 배열을 돌려주고 `flatMap(itemsIn)`).

**7차 — Codex `fail` 1건 (Grok `pass`). 같은 결함의 중첩 변형:**

> *"`### Steps` 아래 `#### Step 1` 은 체크박스, `#### Step 2` 는 번호 목록이면 전체를 한 블록으로 처리해 번호 목록을 버린다. 실제 단계 3개 중 1개만 반환하면서 `valid:true`."*

두 번 연속 같은 뿌리를 맞았다 — **"체크박스가 있으면 그것만"을 블록 전체에 걸었다**는 것. 그 휴리스틱이 옳은 범위는 **연속된 목록 덩어리 하나**다(체크박스 바로 아래 불릿은 그 단계의 설명이다). 그래서 `stepsIn` 을 따로 두고 덩어리 단위로 판단한다 — 제목·산문이 덩어리를 끊는다. 폴백(단계 제목이 아예 없어 Plan A 블록 전체를 볼 때)은 `itemsIn` 의 블록 전체 규칙을 그대로 쓴다. 거기서는 근거·트리거 산문이 섞여 있어 그 규칙이 필요하기 때문이다.

**8차 — Codex `fail` 1건. 같은 계열 세 번째:**

> *"빈 줄로 구분된 체크리스트와 번호 목록을 같은 run 으로 묶고 체크박스만 선택하여 번호 목록의 실행 단계를 버린다."*

세 번 연속 같은 질문을 다르게 물어본 것이다 — **"체크박스 목록은 어디서 끝나는가."** 덩어리(run)라는 개념 자체가 틀린 근사였다. 실제로 배제하고 싶은 것은 **체크박스보다 더 들여쓴 불릿** 하나뿐이다(그건 그 단계의 설명이다). 그래서 규칙을 그것 하나로 줄였다: **같은 들여쓰기면 표기가 무엇이든·빈 줄이 몇 개든 단계이고, 더 깊으면 설명이다.** 산문·제목은 체크박스의 유효 범위를 끝낸다. 이 계열의 변형 4가지를 전부 테스트로 박았다.

**9차 — Codex `fail` 1건. 같은 질문의 마지막 변형:**

> *"Plan A 바로 아래 체크리스트와 하위 `### Step 2` 가 함께 있으면 하위 단계 블록만 추출하여 앞의 체크리스트를 누락한다."*

단계가 **제목 아래에만** 있다고 가정한 것이 남아 있었다. 첫 하위 제목 **앞의 머리말**에서도 걷되 **체크박스만** 걷는다 — 그 자리의 일반 불릿은 대개 전제를 적는 문장이라, 전부 걷으면 조용한 누락을 지저분한 목록과 맞바꾸는 셈이 된다. 체크박스는 그런 모호함이 없다.

**10차 — Codex `fail` 1건. 여기서 접근을 바꿨다:**

> *"단계 제목이 있으면 Plan A 의 머리말과 인식된 단계 블록만 수집하여 다른 하위 제목의 체크리스트를 누락한다. `### Preparation` 의 백업 체크박스와 `### Steps` 의 마이그레이션 체크박스를 함께 넣으면 백업이 빠진 채 `valid:true`."*

다섯 라운드 연속 같은 계열이면 **변형을 막는 것이 틀린 접근**이다. 규칙 하나로 일반화하고 그동안 쌓인 헬퍼 3개(`stepsIn`·`looseCheckboxes`·`preambleOf`)를 **지웠다** — 코드가 줄었다:

- **체크박스는 어디에 있든 단계다.** `### Preparation` 의 백업 체크리스트도 `### Steps` 의 마이그레이션만큼 진짜 작업이다.
- **일반 불릿은 단계 제목 아래에서만 단계다.** 그 밖(근거·Plan B 트리거)에서 걷으면 조용한 누락을 지저분한 목록과 맞바꾸는 것이다.
- **체크박스보다 더 들여쓴 불릿은 그 단계의 설명이다.** 빈 줄은 그 범위를 끝내지 않고, 산문·제목이 끝낸다.

기존 63개 테스트를 **하나도 고치지 않고 전부 통과했다** — 새 규칙이 이전 변형을 전부 포함한다는 증거다.

**11차 — Codex 2건 + Grok 1건. 그리고 두 레인이 같은 결함에 독립적으로 합의했다:**

> *(codex)* *"`### Steps` 아래 `#### Database`·`#### Application` 같은 하위 제목을 만나면 `inSteps` 가 false 로 초기화되어 번호 목록의 실행 단계가 누락된다."*
> *(codex + grok, 동일 지점)* *"단계 추출 결과가 비면 `itemsIn(planA)` 폴백이 Plan A 전체의 일반 불릿을 단계로 승격한다 — `#### 단계` 가 비고 `#### 막힐 수 있는 지점` 에만 불릿이 있으면 그 **트리거가 실행 Todo** 가 된 채 `valid:true`."*

**두 레인 합의는 v3.36 이 3중 게이트를 만든 이유 그 자체다** — 벤더가 다른 둘이 같은 지점을 짚으면 그건 취향이 아니다.

1. `inSteps` 를 불리언으로 둔 것이 틀렸다. 단계 섹션은 **나뉠 수 있다.** 깊이(`stepsLevel`)로 추적해 자식 제목은 범위를 유지하고 형제·상위 제목에서만 벗어난다.
2. **폴백을 없앴다.** 관대한 폴백이 내가 없애려던 실패 모드를 그대로 재생산했다 — 산문을 단계로 승격하고 `valid:true`. 단계를 산문과 구별할 수 없는 계획서에는 **기계가 읽을 단계가 없는 것**이고, 그렇게 말하는 것이 이 게이트의 존재 이유다. 폴백이 사라져 고아가 된 `itemsIn` 도 지웠다.

**12차 — Codex `fail` 1건. 실사용 형태다:**

> *"코드 펜스를 구분하지 않아 bash 예시의 `# Run the backup` 주석을 제목으로 인식하고 Plan A 를 조기에 잘라낸다. 실행 단계 3개 중 이후 2개가 Todo 에서 누락되는데도 `valid:true`."*

계획서는 ```bash 예시로 가득하다 — 이건 이국적인 케이스가 아니라 **평범한 계획서**다. 줄 기반 제목 스캔에 펜스 상태를 넣었다(`sliceHeadingBlocks` 는 스캔이 문서 중간에서 시작하므로 펜스 지도를 미리 계산한다). 덤으로 **예시 안의 체크박스도 단계로 세지 않는다** — 그건 명령 예제지 작업이 아니다.

> **인접 미수정**: `sliceSection`(인벤토리 섹션 슬라이서, v3.32부터 있던 코드)도 펜스를 모른다. 인벤토리 섹션 *안에* 펜스가 있어야 발현하는데 그 섹션은 표라서 실제로는 거의 안 생긴다. 기록만 남긴다.

**13차 — Codex `fail` 1건. 펜스 규칙이 반쪽이었다:**

> *"코드 펜스의 문자·길이를 추적하지 않고 상태를 반전한다. 백틱 4개로 감싼 Markdown 예시 내부의 백틱 3개를 종료로 오인하여 `#` 주석에서 Plan A 가 잘린다."*

또 인스턴스를 막을 뻔했다. 대신 **CommonMark 의 실제 규칙**을 넣었다 — **닫는 펜스는 같은 문자여야 하고 여는 것보다 짧으면 안 된다.** 짧거나 다른 마커는 열린 블록의 *내용*이다. 이 계열은 이걸로 끝난다.

**14차 — Grok `pass`. Codex 2건, 둘 다 CommonMark 정합성:**

> 1. *"닫는 펜스의 후행 문자를 검사하지 않아 코드 블록 안의 ```` ```bash ````를 종료로 오인한다."* — CommonMark 에서 **닫는 펜스는 info string 을 가질 수 없다.** 열린 블록 안의 ```` ```bash ````는 여는 것도 닫는 것도 아니고 예제의 한 줄이다.
> 2. *"체크박스·불릿 정규식이 Markdown 목록 표기인 `+` 를 제외한다."* — 마커는 `-`·`*`·`+` 셋이다.

2번을 고치면서 **`extractGoal`·`extractPlanBTriggers` 도 같이 맞췄다**(둘 다 `-` 만 받고 있었다). 단계 파서만 셋을 받으면, `+` 로 쓴 계획서가 *단계는 읽히는데 성공 기준이 없다*는 엉뚱한 사유로 Phase 0 회귀를 맞는다. 추가는 순증(더 많은 유효 마크다운을 인식)이라 기존 소비자(`/cc` 핸드오프)에 회귀가 없다.

**15차 — Grok `pass`(연속 2회). Codex 1건, 마지막 규격 항목:**

> *"제목 정규식이 선행 공백을 허용하지 않아 유효한 Markdown 제목인 ` ## Plan B` 에서 Plan A 범위를 닫지 못한다. 대체 배포 체크박스까지 Plan A 실행 Todo 에 포함하면서 `valid:true`."*

CommonMark 는 ATX 제목에 **공백 3칸까지** 허용한다. 컬럼 0에 하드 앵커한 패턴이 그걸 놓쳐서, **조건부 우회 작업(Plan B)이 기본 실행 목록에 섞였다.** `^ {0,3}(#{1,6})` 로 고쳤다.

**16차 — Grok `pass`(연속 3회). Codex 1건:**

> *"체크박스 정규식이 번호 목록(`1. [ ]`)을 인식하지 않아 Preparation 아래의 백업·복원 확인 작업이 Todo 에서 누락된다."*

번호 태스크 리스트는 유효한 GFM 이다. 못 읽으면 그것들이 **일반 불릿**으로 떨어지고, 단계 제목 밖이면 그대로 버려진다. 체크박스 인식에 `1.`·`1)` 을 더했다(`extractGoal` 도 같이).

**17차 — Codex 2건, 여기서 루프를 끊었다:**

> 1. *"여러 줄 HTML 주석 안의 제목도 실제 제목으로 인식해 Plan A 를 조기에 종료한다."* — `/cp` 템플릿의 안내 주석이 실제로 여러 줄이다. 줄 단위로 주석을 걷어내면 **주석 속살이 문서에 남는다.** 전체 텍스트에서 주석을 공백으로 치환하되 줄 수는 보존하도록 바꿨다.
> 2. *"백틱 펜스의 info string 에 백틱이 있는지 검사하지 않아 인라인 코드로 시작하는 설명문을 열린 코드 블록으로 오인한다."* — CommonMark: 백틱 펜스의 info string 에는 백틱이 올 수 없다.

**여기서 멈춘 이유**: 12차 이후 지적은 전부 마크다운 규격 정합성이고, 라운드마다 새 변형이 나오지만 **`/cp` 템플릿과 `generatePlanContent()` 가 실제로 만드는 형태는 74개 테스트로 전부 덮였다.** Grok 은 14·15·16차 연속 `pass`. 남은 것은 사람이 손으로 쓸 수는 있으나 이 레포가 생성하지 않는 모양들이라, 발견되면 그때 고치는 편이 싸다.

**이 계열(6~17차)의 교훈**: 파서가 문서를 *한 가지 모양*으로 가정할 때마다 게이트는 **조용히 짧은 목록을 통과시켰다.** 짧아진 걸 아무도 못 본다는 것이 이 작업이 없애려던 실패 모드 그 자체여서, 변형 7가지를 전부 테스트로 고정했고, 마지막에는 그것들을 **규칙 하나**로 대체했다.

자체 검토로 추가 발견·수정한 결함 2건:

1. **값 없는 플래그가 무한 루프.** `--timeout` 만 주고 값을 생략하면 파싱 루프가 영원히 돈다 — `set -e` 가 없어서 `shift 2` 는 인자가 1개일 때 shift 도 exit 도 하지 않는다. **행(hang)은 여기서 가장 나쁜 실패 모양이다**(출력도 종료 코드도 안 남는다). `need_val` 아리티 검사 + 10초 상한 회귀 테스트.
2. **`elapsed` 가 레인별이 아니었다.** 보고 루프가 `wait` 전체 이후에 돌기 때문에 시계를 거기서 읽으면 **빠른 엔진이 가장 느린 엔진의 벽시계를 뒤집어쓴다.** 실측: 수정 전 grok·codex 둘 다 35초 → 수정 후 **grok 11초 / codex 13초**. 어느 엔진이 기다릴 값어치가 있는지가 이 숫자의 존재 이유라 그냥 두면 안 됐다. 완료 시각을 서브셸 안에서 찍도록 바꿨다(`rc=$?; echo "$rc $(date +%s)"`).

> **인접 결함 2건 (이번에 안 고침 — 기록만)**
>
> 1. `scripts/cross-verify.sh` 도 같은 자리에 같은 계측 결함이 있다 — 1차 실행에서 codex 산출물은 20:04:36 에 나왔는데(≈64초) `elapsed=420s` 로 보고됐다. 보고 루프가 `wait` 전체 이후라서다.
> 2. `scripts/grok-review.sh` 의 JSON 언랩이 **다중 객체 스트림을 못 읽는다.** Grok 은 진행 상태 객체를 여러 개 흘린 뒤 마지막에 판정을 내는데, `body.match(/\{[\s\S]*\}/)` 그리디 매칭이 전부를 한 덩어리로 잡아 파싱에 실패한다. 게이트가 **거짓 pass 를 내지는 않았다**(`unparsable` = 투표 안 함, 설계대로 정직하다). 하지만 **큰 diff 에서 3번째 레인이 사실상 무력화**되므로 별도 수정이 필요하다. 마지막 well-formed 객체를 취하는 방식은 `cross-verify.sh` 의 EXTRACT 가 이미 쓰고 있다.
