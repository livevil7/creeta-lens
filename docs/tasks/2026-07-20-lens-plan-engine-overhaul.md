# Lens 계획 엔진 개편 — 기획서 품질 게이트 · 모델 배분 통제 · /cs PR 전환 · /cpp 정리

> 이 문서 자체가 새 deep 골격의 실물 견본이다. 도입하려는 섹션 구성을 그대로 따른다.

## 🎯 What — 목표 (무엇이 가능해지는가)

**이 작업이 끝나면 가능해지는 것:**

- 관리자가 Lens가 만든 기획안 하나만 읽고 **승인/반려를 판단할 수 있다.** 지금은 "무엇을 만드는지"가 빠져 있어 판단 근거가 부족하다.
- 계획서에 **"왜 이 방법을 골랐고 무엇을 버렸는지"가 남는다.** 지금은 결론만 있고 선택의 근거가 없다.
- **깊이가 얕은 계획서로는 실행이 시작되지 않는다.** 필수 항목이 비면 `/c`·`/cc`가 실행을 거부한다. 어떤 경로로 만들어진 계획이든(과거 문서·수동 작성·다른 세션 산출물) 동일하게 걸린다.
- **최상위 모델이 필요한 일에만 쓰인다.** 파일 읽기·자료 수집 같은 단순 업무가 최상위 모델을 먹지 않고, 어떤 모델이 몇 번 쓰였는지 사용자가 확인할 수 있다.
- **`/cs`로 푸시한 변경이 전부 PR로 남는다.** 기본 브랜치에 직접 밀어 넣는 경로가 사라진다.
- 계획 스킬이 **`/cp` 하나 · 등급 3개(fast/standard/deep)**로 정리된다.

**완료의 정의 (Done = ?):**

> 새 골격으로 만든 계획서 한 건이 실제로 `/cc` 실행 진입 게이트를 통과하고, 같은 세션의 에이전트 모델 사용 내역이 기록으로 확인되며, `/cs` 한 번이 PR을 만들어 기본 브랜치 직접 푸시 없이 동기화를 끝낸 것이 실행으로 확인된다.

## 🚧 비목표 (Non-Goals)

> "합리적으로 목표가 될 수 있었으나 이번엔 하지 않는 것."

- **기존 계획서 80건의 소급 개정** — 하지 않는다. 완료된 history 문서를 새 골격으로 다시 쓰는 것은 가치가 낮다. 대신 실행 진입 게이트가 낡은 계획을 *실행 시점에* 잡는다.
- **계획서 품질의 의미적(semantic) 자동 판정** — 하지 않는다. "대안이 진짜로 검토됐는지", "리스크가 현실적인지"는 규칙 검사로 판정 불가능하다(Codex 지적). 구조적 항목만 기계로 막고, 의미 품질은 사람 승인과 독립 검토에 맡긴다.
- **모델 자동 선택기 고도화** — 하지 않는다. 이번엔 "명시 의무 + 상한"까지만. 복잡한 자동 선택 로직은 과잉이다.
- **Codex로 적대적 검증 전면 대체** — 하지 않는다. 독립 검토 1개 역할만 시험한다. 광범위 대체는 결과 형식·판단 기준이 달라져 통합 비용이 커진다.
- **전 레포 squash auto-merge** — 이번 범위 밖. PR-only까지만 하고 자동 병합은 별도 단계로 뺀다(미해결 질문 Q1 참조).
- **`/ccp` 파이프라인 재설계** — 모델 배분만 손대고 검증 로직은 건드리지 않는다.

## ❓ Why — 왜 해야 하는가 (6하원칙)

- **왜 지금**: 세 문제가 동시에 임계에 왔다. ① 기획서 80건 전수조사에서 NFR·인수기준·미해결질문·테스트케이스 표가 **단 한 번도 등장하지 않았다(0/80)**. ② 최상위 모델(fable) 사용량이 구독의 50%에 도달했다. ③ `/cs`가 26개 레포에 **기본 브랜치 직접 푸시**를 계속하고 있어 검토 기록이 남지 않는다.
- **무엇을**: 계획서 골격에 결손 섹션을 넣고, 그 골격을 *실행 진입 시점에* 강제하고, 모델 배분을 계측·상한으로 통제하고, `/cs`를 PR 경유로 바꾼다.
- **어떻게**: 산문 규칙을 늘리는 게 아니라 **집행 지점을 옮긴다.** 작성 시점 검사는 우회 경로가 많아(응답 본문으로만 계획을 내는 경우·외부 수정·과거 문서) 실효가 없다. 실행 진입은 우회가 불가능하다.
- **누구를 위해**: 기획안을 읽고 승인하는 관리자(사용자 본인), 그리고 그 계획을 받아 실행하는 `/cc` worker.
- **어디서**: creeta-lens 리포 → 새 버전 출시 → 이 컴퓨터 우선 적용, 다른 머신은 각자 업데이트 시.
- **안 하면**: 기획안은 계속 "실행 로그에 가까운 문서"로 남아 승인 판단에 못 쓰이고, 최상위 모델 쿼터는 단순 업무에 계속 소모되며, 코드 변경 이력에 검토 기록이 남지 않는다. 그리고 이번에 확인된 **"딱지와 내용이 불일치하는 계획서"**(`planner: cpp`인데 71줄, 하드게이트 전무)가 계속 생산된다.

## 📖 용어 풀이 (운영자용)

| 용어 | 쉬운 설명 |
| --- | --- |
| **골격 / 스켈레톤** | 계획서에 반드시 들어가야 하는 섹션 목록. 지금은 What/Why/How/Review 4개 축. |
| **비목표(Non-Goals)** | "할 수도 있었지만 이번엔 안 한다"고 못 박는 것. 범위가 슬금슬금 늘어나는 걸 막는다. |
| **검토된 대안** | 최종안 말고 검토했다가 버린 방법들과 버린 이유. 첫 아이디어를 그냥 적었는지, 실제로 고민했는지가 여기서 드러난다. |
| **차단 질문** | 답이 없으면 실행을 시작할 수 없는 질문. 답이 없어도 진행 가능한 질문(비차단)과 구분한다. |
| **게이트** | 조건을 못 채우면 다음 단계로 못 가게 막는 관문. |
| **실행 진입 게이트** | 계획을 *쓸 때*가 아니라 *실행을 시작할 때* 검사하는 관문. 어떤 경로로 만든 계획이든 실행하려면 반드시 통과해야 해서 우회가 안 된다. |
| **TOP (최상위 티어)** | 난이도 사다리의 맨 윗칸. 현재 실물은 fable. 이름이 아니라 상대 위치라 새 모델이 나오면 자동으로 올라간다. |
| **상속** | 에이전트를 띄울 때 모델을 지정하지 않으면 부모 세션 모델을 그대로 물려받는 것. 부모가 fable이면 자식도 fable. |
| **fan-out** | 하나의 조사를 여러 갈래로 쪼개 에이전트를 동시에 여러 개 띄우는 것. |
| **squash 병합** | 여러 커밋을 하나로 합쳐 넣는 병합 방식. **원격에 새 커밋이 생기므로** 로컬에 남은 원본 커밋과 갈라진다. |
| **fail-closed** | 실패했을 때 우회하지 않고 그냥 멈추는 것. 반대는 "실패하면 예전 방식으로 몰래 진행". |

## 🧰 실행 전략 & 자원

- **난이도**: **deep** — 되돌리기 어려운 변경(스킬 폐지·푸시 방식 전환)이 포함되고, 5개 스킬 + 훅 + 셸 스크립트에 걸쳐 있으며, `/cs` 변경은 26개 레포의 운영 동기화에 직접 영향.
- **권장 모델**: 설계·게이트 로직은 TOP(현재 fable). 문구 일괄 치환·참조 갱신은 중간 티어. 파일 목록 수집은 경량 티어.
- **병렬 실행**: 작업 패키지 1·3은 서로 독립이라 병렬 가능. 패키지 2는 같은 파일(`cp/SKILL.md`)을 여러 갈래로 건드리므로 **순차**.
- **활용 스킬·도구**: codex CLI(교차 검증 — 이미 1회 수행), `gh`(PR), node(기존 의존), git. Playwright 불필요(화면 작업 없음).
- **기존 자원 재사용**:
  - `lib/plan-manager.js`의 `validatePlanStructure()` + `SECTION_ALIASES` — 죽어 있지만 **다국어 별칭 로직은 살아 있어 재사용 가능**. 새로 만들지 않는다.
  - `hooks/pre-tool-task.js` — 이미 `tool_input`을 받고 있어 `model` 기록에 신규 배선 불필요.
  - `scripts/bump-version.sh` — 14곳 일괄 버전 갱신.
  - `scripts/git-sync-all.sh` — 순수 POSIX 셸. 이 성질을 유지한다.

## 🛠 How — 어떻게

> 순서는 Codex 권고를 따른다: **한 번에 다 바꾸면 회귀 원인을 구분할 수 없다.** 패키지 단위로 순차 적용하고 각 패키지마다 검증한다.

### 패키지 1 — 모델 배분 통제 (1순위)

> 근거: 가장 작고 외과적이며 즉시 효과가 난다. **현재 정책을 완벽히 지켜도 fable을 많이 쓰도록 설계돼 있다**(Codex 교정) — 계측만으론 못 줄인다. 계측과 정책을 함께 바꾼다.

- [ ] **1-1. 모델 계측** — `hooks/pre-tool-task.js`가 `toolInput.model`·`toolInput.subagent_type`을 읽어 `registerAgent()`에 전달. `lib/agent-tracker.js`의 agent 엔트리에 `model`·`agentType`·`skill` 필드 추가.
      - 파일: `hooks/pre-tool-task.js` · `lib/agent-tracker.js`
      - 검증: 에이전트 1개 spawn 후 `.lens/agent-dashboard.json`에 model 값 존재
      - ⚠️ **한계 명기**: 모델을 생략(상속)하면 `tool_input.model`이 `undefined`다. 실제 실행 모델을 훅이 알 방법이 없다. → 1-2가 이 구멍을 막는다.
- [ ] **1-2. 모델 미지정 스폰 금지** — 5개 스킬(`c`·`cc`·`ccp`·`cp`·`cpp`)의 spawn 지시에서 "TOP이면 지정 생략(상속)" 규칙을 **폐기**하고 **항상 명시 지정**으로 바꾼다.
      - 이유: 상속이 계측 구멍이자 fable 소비의 직접 원인. 명시하면 기록되고, 기록되면 통제된다.

### 패키지 3 — `/cs` PR 전환 (3순위)

> Codex 권고 반영: **PR-only 먼저, auto-merge는 별도 단계.** 현재 제안 그대로면 PR을 만들 수 없거나 동기화를 깨뜨린다.

- [ ] **3-1. 커밋 전 임시 브랜치** — 가장 중요. 기본 브랜치에서 커밋한 뒤 PR을 만들면 **비교할 변경이 남지 않는다.** dirty 감지 시 커밋 *전에* `sync/<날짜>-<해시>` 브랜치를 만들고 거기서 커밋한다. 기본 브랜치는 원격과 동일하게 유지.
- [ ] **3-2. base 결정 규칙** — 각 레포의 실제 기본 브랜치. **`Returns_ERP_v20`은 `staging`으로 고정하고 자동 병합 대상에서 제외**(staging→main 승격은 `promote-to-main.sh` 별도 규칙, 운영 배포 직결).
- [ ] **3-3. 중복 PR 방지** — 열린 동일 PR이 있으면 재사용, 없으면 생성. 재실행해도 중복 커밋·PR이 안 생겨야 한다.
- [ ] **3-4. fail-closed** — PR 생성 실패 시 **기본 브랜치 직접 push로 우회 금지.** 실패로 보고하고 멈춘다. (우회하면 사용자가 요구한 "PR 보장"이 조용히 무너진다.)
- [ ] **3-5. 병합 후 로컬 복귀** — 병합 확인 후 기본 브랜치로 돌아와 fast-forward. squash가 원격에 새 커밋을 만들므로 이 단계가 없으면 다음 `/cs`가 즉시 `diverged`로 멈춘다.
- [ ] **3-6. 미병합은 "동기화 완료"로 보고 금지** — 병합 대기 중인 변경은 운영 머신이 못 받는다. 보고에 명시.
- [ ] **3-7. `.github/workflows/` 사전 감지** — `gh` 토큰에 `workflow` 스코프가 없어 해당 변경이 낀 푸시는 거부된다. 미리 감지해 실패 목록에 명시.

## 🔀 검토된 대안 (Alternatives Considered)

> 이 섹션이 이번 개편의 핵심 신설 항목이다. 최종안이 목표에 비추어 최선임을 증명한다.

**대안 A — 계획서에 섹션을 대폭 추가하고 등급별 최소 줄 수를 강제**

- *Good, because* 결손 섹션(NFR·대안·미결질문)이 확실히 표면화된다.
- *Bad, because* **줄 수를 품질 대리값으로 쓴다.** 이미 중앙값 153줄인데 만족스럽지 않았다는 사실 자체가 길이≠품질을 증명한다. 각 섹션을 한 줄로 때워도 형식 검증은 통과한다. 작은 작업의 계획 비용이 실행 비용을 넘는다.
- **기각.** 대신 필수 7항목 + 조건부 부록 + 위험도 기반 등급으로 축소.

**대안 B — 작성 시점 훅(PostToolUse)으로 계획서를 검사**

- *Good, because* 잘못된 문서가 애초에 저장되지 않는다.
- *Bad, because* 우회 경로가 많다 — 다른 파일 쓰기 경로는 훅 대상이 아니고, 파일을 안 쓰고 응답 본문으로만 계획을 내면 검사가 아예 안 돌며, **외부 수정·과거 버전 문서는 생성 시점 훅을 거친 적이 없다.**
- **기각.** 실행 진입 게이트로 대체 — 어떤 경로로 만든 계획이든 실행하려면 통과해야 하므로 우회 불가. 소급 정리가 불필요해지는 것도 이 선택의 부산물.

**대안 C — `/cpp`를 즉시 폐지하고 `/cp`에 통합**

- *Good, because* 등급 체계가 한 곳에 모이고 골격 동기화 실패가 사라진다.
- *Bad, because* 독립 검증 2건이 "품질 문제 해결 전 인터페이스 변경"을 지적했다. 지금 `/cp`는 고정 Plan A/B, `/cpp`는 Body-Adaptive로 **구조 철학이 다르다** — 정도 차이가 아니라 종류 차이.
- **조건부 채택 — 순서를 바꿔서.** 2A(골격 통일)가 `/cp`를 Body-Adaptive로 옮기면 그 차이가 소멸한다. 차이가 사라진 뒤 2C에서 폐지한다. 같은 릴리스 안에서 순서만 지킨다.

**대안 D — deep 파이프라인을 `skills/cp/deep.md`로 분리해 조건부 Read**

- *Good, because* `cp/SKILL.md` 비대화를 막는다.
- *Bad, because* **보장된 로드가 확률적 툴콜로 격하된다.** 지금은 `/cpp` 호출 시 하드게이트 조항이 무조건 로드되는데, 조건부 Read가 실패하면 인라인 기본값(degrade)이 조용히 적용돼 안전조항이 티 안 나게 무력화된다. 이 레포에 frontmatter 분기 실패 사고 이력도 있다(CHANGELOG:50). 게다가 정책은 인라인에 남겨야 하므로 **파일이 오히려 커진다** — 원래 동기가 무너진다.
- **기각.** 정책·게이트는 인라인 유지. 크기 문제는 `/cpp` 병합 시 중복 소멸(비교표·라우팅 안내가 존재 이유를 잃음) + `/cp` 저빈도 모드 외부화로 해결.

**대안 E — `/cs`를 PR + squash auto-merge로 (당초 선택)**

- *Good, because* PR 기록이 남으면서 동기화도 안 끊긴다.
- *Bad, because* **auto-merge가 즉시 실행되면 PR은 검토 단계가 아니라 기록용 포장에 불과하다**(Codex). 즉 "PR 무조건 생성"의 원래 취지(검토 기록)를 자기부정한다. 또 검사 실패·auto-merge 미허용 시 변경이 기본 브랜치에 영영 도달하지 않고, staging 자동 병합은 승인 없는 배포를 촉발한다.
- **보류.** PR-only를 먼저 시행하고 auto-merge는 별도 단계로. → 미해결 질문 Q1.

**대안 F — `/ccp` 적대적 검증을 Codex로 광범위 대체**

- *Good, because* fable 부하가 다른 공급자로 넘어간다.
- *Bad, because* 결과 형식·판단 기준이 달라져 통합 비용이 커지고, 전체 비용·지연·일관성이 개선된다는 근거가 없다. Codex 타임아웃 사고 2건이 보여주듯 신뢰성도 미검증.
- **축소 채택.** 독립 검토 **1개 역할만** 시험하고 품질·비용을 비교한 뒤 확대 여부 결정.
