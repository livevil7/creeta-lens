agentmemory — 네임스페이스가 뒤엉켰다

프로젝트 키 = basename(git top-level ?? cwd). 머신 차원 없음 · 대소문자 정규화 없음 · 워크스페이스 루트 개념 없음.

잘못 합쳐짐 · 192세션

서로 다른 두 컴퓨터가 한 네임스페이스로

Git = c:\Users\user\...(120) + c:\Users\livev\...(72). 물리적으로 다른 PC 두 대의 경로·설치상태·SSH 사실이 구분 없이 섞여 회상된다.

잘못 갈라짐 · 76세션

GIT(ADMIN PC) vs Git(나머지). 같은 주제를 물어도 어느 컴퓨터냐에 따라 다른 과거가 나온다.

파일 메모리 · 설치목록 · 동기화

머신 구분 부재 · 진짜 아픈 곳

130개(49%)가 머신 한정 사실인데 무태그

SSH·디스크·launchd·경로처럼 "이 머신에서만 참"인 사실이 공유 풀에 그대로 섞여 있다. sj-omen에서 물어도 Mac Mini의 상태가 근거로 딸려 나온다. 프론트매터 machine 태그가 필요하다.

배선 불일치 · 오판 정정

머신마다 연결 방식이 다르다

Mac Mini·SJ_X1은 정식 autoMemoryDirectory(267개 실측·cron pull 정상), sj-omen만 구식 <JUNCTION>. ⚠️ 최초 조사에서 projects/<key>/memory를 세어 "Mac Mini 0건"이라 오판했다 — 그 경로는 설정이 대체하는 바로 그 경로였다.

지운 게 되살아난다

설치목록 SoT 4개가 전부 다름

~/.claude/lens/manifest.json에 오늘 지운 ponytail과 영구 제거한 understand-anything이 아직 있다. 제거 경로 어느 것도 이 파일을 갱신하지 않는다.

기록이 지워진다

/cs의 reset --hard가 메모리를 되돌린다

대상 레포 livevil-setting이 곧 메모리 정션의 타깃이다. 2026-08-02에 라이브 메모리 17건이 이 경로로 실제 소실됐다.

커버리지 구멍

/cs가 Mac Mini 진짜 레포를 못 본다

스캔 루트에 $HOME이 없다. 실제 작업 레포 4개는 홈 직속(~/livevil-setting 등)이라 한 개도 안 잡히고, 대신 2월에 멈춘 옛 클론 더미를 훑는다.

드리프트

배포본 ≠ 실물 (5곳) · Lens 버전 불일치

배포본으로 새 PC를 세팅하면 지금과 다른 환경이 나온다. 실물 훅은 C:\Users\ADMIN 절대경로 하드코딩. Lens는 sj-omen 3.29.0 / macmini 3.28.0.

05 / 11 · GOAL

목표

Done = 아무 두 대를 골라 같은 질문을 던졌을 때, 공통 사실은 똑같이 나오고 머신 고유 사실은 각자 자기 것만 나온다.

섞이지 않는다 — 어느 컴퓨터에서 물어봐도 그 컴퓨터의 사실과 다른 컴퓨터의 사실이 구분되어 나온다.
사라지지 않는다 — 한 컴퓨터에서 정리한 내용이 다른 컴퓨터에서도 그대로 보인다. 한쪽에만 있는 일이 없어진다.
되살아나지 않는다 — 지웠다고 하면 어느 컴퓨터에서 무슨 명령을 돌려도 다시 안 깔린다.
동기화가 기록을 지우지 않는다 — /cs가 메모리를 되돌리는 사고가 재발하지 않는다.
문서가 현실과 일치한다 — "설정 X가 되어 있습니다"라고 말하면 실제 파일이 그렇다.

핵심 설계 — 정체성 2축: 지금 고장난 이유는 "어느 프로젝트인가"와 "어느 컴퓨터인가"를 한 개의 문자열로 표현하려 했기 때문이다. workspace_id(논리) 와 machine_id(물리) 를 분리하고, scope(global / workspace / machine) 로 "이 사실이 어디까지 참인가"를 명시한다. 머신 표준은 sj-omen · sj-rog · sj-x1 · macmini 4종.

P2

네임스페이스 정상화

검증: 4대에서 각 1세션 후 키 4종이 정확히 찍히는가.

왜 과거를 재키잉하지 않나 — 홈디렉터리 세션 34건은 머신은 알아도 어느 프로젝트인지 불명이고 undefined 6건은 아무것도 모른다. 40건(12%)이 원리적으로 복원 불가다. 반면 재키잉은 9,725건 관측의 외래키를 전부 다시 쓰는 작업이라, 얻는 것 대비 잃을 수 있는 것이 비대칭이다.

09 / 11 · ALTERNATIVES

검토된 대안 · Codex 교차 협의

Codex 협의 통과(RC=0). 근본 결함 지목이 일치했다 — "프로젝트·머신 정체성에 대한 단일 규격과 SoT가 없다".

대안 A · 기각

agentmemory를 포크해 로직을 고친다

Good: 설정 누락 위험 0, 새 머신에서도 자동으로 옳다. Bad: 남의 레포라 업데이트마다 재적용해야 하고 /cu가 업데이트를 자동 실행하므로 조용히 원복된다. → 공식 스위치가 있는데 포크할 이유가 없다.

대안 B · 기각

agentmemory를 버리고 파일 메모리로 통합

Good: 계층이 하나면 정체성 문제도 하나. Bad: 자동 수집 9,725건이 사라지고 MCP 도구 20여 개 철거 비용. → 문제는 계층 수가 아니라 정체성 규격 부재다.

대안 C · 기각

agentmemory도 전체 경로를 키로

Good: 절대 안 섞이고 구현이 쉽다. Bad: 머신마다 완전 격리되어 공통 지식 공유가 0이 된다. 대소문자·사용자명 문제도 그대로 남는다. → 정밀도를 얻고 공유를 잃는 거래.

대안 D · 기각

workspace_id를 레포 단위로 잘게

Good: 회상 정밀도 상승. Bad: 지금 이미 그렇고, 그게 문제의 일부다 — 루트에서 열었냐 하위에서 열었냐로 갈린다. 레포×머신 = 100개 넘는 네임스페이스. → 정밀도보다 일관성이 먼저.

채택 · Codex 분기 해소

계층별로 나눠 적용

Codex는 A/B 중 하나를 고르라는 전제로 답했다. 이 계획은 agentmemory=키에 머신 포함 / 파일메모리=단일 풀+머신 태그로 나눈다. 각 대안의 단점이 계층 특성과 정확히 상보적이기 때문 — 자동 로그에서 "공통 지식 중복"은 문제가 아니고, 267건 수동 큐레이션에서 "태그 누락"은 관리 가능한 규모다.
