03 / 06 · GOAL

목표 — 무엇이 가능해지는가

왜: 작업 중간 상태가 통합 브랜치에 바로 쌓여 "지금 main 이 배포 가능한가"를 알 수 없고, staging 체크아웃 레포는 커밋 보호에서 아예 빠져 있다.

자기 브랜치에서 작업 — 새 작업을 시작하면 그 작업만의 브랜치에서 코드가 바뀐다. 통합 브랜치가 중간 상태로 오염되지 않는다.
병합 확인 후 완료 — 완료 처리하면 변경이 리뷰 가능한 상태로 올라가고, 병합이 확인된 뒤에야 완료 기록으로 내려간다. "문서상 완료인데 코드는 어디 있는지 모르는" 상태가 사라진다.
브랜치 자동 소멸 — 병합이 끝난 브랜치는 없어진다. 브랜치 목록을 열면 지금 진행 중인 작업만 보인다.
배포 오트리거 차단 — 배포 환경이 있는 레포에서 작업이 실수로 배포를 트리거하지 않는다. 지금은 막혀 있지 않다.
병렬 작업 안전 — 여러 worker 가 동시에 같은 레포를 고쳐도 서로의 변경을 지우지 않는다.
Done = ?

아무 레포에서나 새 작업을 계획하고 실행한 뒤 완료 처리했을 때, 그 작업의 코드가 자기 브랜치에서 리뷰를 거쳐 통합 브랜치에 들어가 있고, 그 브랜치는 지워져 있고, 완료 기록 문서가 남아 있다.

소유권 재배치 + 10개 태스크

/cp 가 이름을 정하고 · /cc 가 만들어 그 위에서만 커밋하고 · /cp done 이 PR·머지·삭제로 닫는다. /cs 는 task 브랜치를 소유하지 않는다.

05 / 06 · RISKS

리스크 레지스터

Claude(세션 컨텍스트) + Codex(독립 코드 분석) 듀얼 조사. 핵심은 생성 자동화가 누적 문제를 가속하는 것과 staging 오배포.

R1 · 높음

브랜치 자동 생성이 누적을 가속

트리거: requireTaskBranch:true 후 임의 레포 원격 브랜치 5개 초과. → T8(prune)을 같은 릴리즈에 묶고 T0 를 완료 조건으로. 중단: T8 미완이면 true 로 올리지 않는다.

R2 · 높음 (운영 사고)

Returns_ERP_v20 staging 오배포

트리거: base 판정이 staging 을 놓쳐 main 을 base 로 PR, 또는 staging 직접 커밋. → config 명시값 우선 + 이 레포를 첫 검증 대상. 중단: 감지 base ≠ config 명시값이면 그 레포 실행 차단.

R3 · 중간

병렬 worker 변경 유실

트리거: 같은 파일 대상 worker 2개 이상. → worktree 격리 + hook-utils.js lock 으로 Leader 직렬 통합. 중단: 충돌 1회 감지 시 순차 강등.

R4 · 중간

gh 부재 · workflow 스코프

트리거: T5 검증에서 PR 실패 레포 3개 이상. → Plan B(로컬 머지 모드) 전환, 레포별 오버라이드. 중단: 3레포 이상이면 mergeMode:"local".

R5 · 중간

기존 stale 브랜치·열린 PR 충돌

트리거: T0 없이 T2~T6 도입. livevil-research 는 지금 base 아닌 브랜치에 체크아웃돼 있어 resolveBase 가 그 피처 브랜치를 base 로 판정한다. 중단: T0 미완이면 T2 검증 실행 금지.

R6 · 낮음

patch-id 로 머지 증명 불가

리베이스 충돌 해결 이력이 있는 브랜치(task/community-insight-surface-v3). → 자동 삭제 제외, 유지 로 남겨 사람이 확인. 추측 삭제 금지.

⚠️ 지금 존재하는 결함 (before/after 대조가 곧 증거)

/cc Phase 7.4 의 브랜치 보호는 main·master 문자 비교다. Returns_ERP_v20 은 staging 체크아웃(GitHub default 는 main)이라 보호에서 빠지고 staging 에 직접 커밋된다 — staging 은 배포 트리거다. 이것이 현재 유일한 배포 사고 경로다.
