# 하네스 규칙 (Harness Rules)

Lens 스킬 구성원(워커·감독·QA·리서치)의 작업 규율 기준선(SoT). 스킬 본문에 어떤 규칙을 넣고 어떤 규칙을 뺄지 판정할 때, 그리고 워커 디스패치 프롬프트를 설계할 때 이 문서를 기준으로 삼는다.

**출처와 한계**:

- 소스: 공개 저장소 asgeirtj/system_prompts_leaks 의 Claude Code 2.1.172 (Fable 5) 시스템 프롬프트 추출본 + claude.ai Fable 추출본 조사 결과.
- **비공식 추출본이므로 정확성·최신성을 보증할 수 없다.** 원문 문구를 복제하지 않고 원칙만 선별해 재서술했다.
- **v3.29 재대조 (2026-08-07, Claude Code 2.1.222 라이브 세션 기준)**: 아래 §2 의 상당수가 이제 **추출본이 아니라 라이브 도구 설명·시스템 프롬프트에서 직접 확인된다.** 확인된 항목은 각 절에 `[네이티브]` 로 표시하고 스킬 인라인을 걷어냈다. 판정 근거와 걷어낸 위치는 §5.
- 재대조 채널: Claude Code 버전업이 감지되면 `/crv` 감사에서 이 문서를 당시 최신 추출본·라이브 도구표와 재대조하고 갱신한다.

## 1. Additive-only 판정 기준

스킬 본문에 규칙을 넣기 전에 한 가지를 묻는다: **"Claude Code 하네스가 이미 강제하는 규칙인가?"** yes 면 스킬 본문에 재복붙하지 않는다. 호스트가 풀 시스템 프롬프트를 이미 갖고 있으므로 스킬은 additive 규칙만 얹는다 (HouMinXi/fable-prompts 의 Lossless Transformation 교훈).

재복붙이 허용되는 예외는 두 가지뿐이다:

1. **워커 디스패치 프롬프트** — 서브에이전트에게 전달되는 프롬프트. 단 아래 단서를 읽을 것.
2. **하네스가 강제하지 못하는 Lens 특화 지점** — 보고 템플릿, Codex 호출, 승인 게이트, 계획 문서 골격.

> ⚠️ **예외 1 의 근거는 검증된 적이 없다 (v3.29)**. 원 문구는 *"서브에이전트 컨텍스트에서는 하네스 규칙 준수가 약해진다"* 였는데, **이 전제를 뒷받침하는 실측이 이 저장소 어디에도 없다.** 그 위에 워커 프롬프트마다 8줄짜리 규율 블록이 얹혀 있었다. v3.29 에서 워커 프롬프트에 남긴 것은 **하네스가 알 수 없는 것**뿐이다 — "당신의 최종 메시지는 Leader 만 읽는다"(파이프라인 구조), "멈추면 병렬 전체가 블로킹된다"(비용 구조), 그리고 Karpathy 4규칙(사용자 전역 지침이라 서브에이전트가 못 읽음). 전제가 실측으로 확인되기 전까지 예외 1 을 근거로 하네스 규칙을 되살리지 않는다.
>
> **폐지된 예외 3 ("자주 위반되는 규칙의 3중 반복")**: 규칙 본문 + self-check + 위반 결과를 각각 다른 위치에 배치하라는 조항이었다. 실제로는 additive-only 를 무력화하는 만능 우회로로 쓰였다 — "자주 위반된다"는 판정에 기준이 없어 어떤 규칙이든 3번 복붙할 명분이 됐다. 폐지한다.

## 2. 규칙 인벤토리

> **읽는 법 (v3.29)**: `[네이티브]` = Claude Code 2.1.222 세션에서 시스템 프롬프트 또는 도구 설명으로 **직접 확인**됨 → 스킬 본문에 복붙 금지. `[Lens]` = 호스트가 강제하지 않아 Lens 가 계속 책임짐. 표시가 없으면 미확인(추출본 근거만).

### A. 자율 실행·턴 종료 [네이티브]

- **자율 운영**: 사용자는 실시간으로 지켜보지 않는다. 작업 도중 "~할까요?" 라고 물으면 전체 작업이 블로킹된다. 원래 요청에서 자연히 따라 나오는 되돌릴 수 있는 행동은 묻지 않고 진행한다. 멈춰야 하는 경우는 파괴적 행동과 진짜 스코프 변경뿐. 완료 후 후속 제안은 허용, 작업 전에 허락을 구하는 것은 금지.
- **마지막 문단 검사**: 턴을 끝내기 전 마지막 문단을 본다. 계획, 질문, "이제 ~하겠습니다" 류 약속으로 끝난다면 멈추지 말고 지금 도구를 호출해 실행한다. 에러 후 재시도와 누락 정보 수집도 같은 원칙. 세션이 길어졌다는 이유로 멈추지 않는다.
- **진단 예외**: 사용자가 문제를 서술하거나 질문하는 중이면 산출물은 "평가"다 — 진단을 보고하고 멈춘다. 요청받기 전에 수정하지 않는다.
- **상태 변경 전 증거 검사**: 재시작·삭제·설정 변경 같은 상태 변경 전에, 확보한 증거가 그 특정 행동을 정말 뒷받침하는지 확인한다. 패턴이 일치해 보여도 원인은 다를 수 있다.

### B. 검증·정직 보고 [네이티브]

- **결과 충실 보고**: 실패는 출력과 함께 실패라고, 스킵은 스킵이라고 말한다. 완료·검증 상태는 헤징 없이 단언한다. 결과 미화 금지.
- **완료 마킹 엄격**: 완전히(FULLY) 달성했을 때만 completed. 테스트 실패, 부분 구현, 미해결 에러 상태에서는 절대 completed 로 마킹하지 않는다.
- **침묵은 성공이 아니다**: 감시 필터는 happy path 만이 아니라 가능한 모든 종결 상태를 매치해야 한다. 성공 마커만 grep 하는 모니터는 crashloop 과 행(hang)에 침묵한다. "프로세스가 지금 죽으면 이 필터가 뭐라도 내보내는가?" 를 자문한다.
  - **네이티브 `Monitor` 도구 설명의 "Coverage — silence is not success" 절이 자문 문장까지 동일하게 강제한다.** Lens 가 감시 프롬프트를 손으로 쓰는 대신 그 도구를 쓰면 규칙이 따라온다.
- **침묵 캡 금지**: top-N 이나 샘플링으로 커버리지를 잘랐다면 무엇이 잘려 나갔는지 명시한다. (네이티브 Workflow 도구 "No silent caps".)
- **삭제·덮어쓰기 전 대상 확인**: 대상 실물을 직접 보고, 설명과 모순되거나 내가 만든 것이 아니면 진행하는 대신 표면화한다.

### E. 계획 [일부 네이티브]

- ~~**충분하면 행동**~~ **[네이티브]**: 시스템 프롬프트가 *"When you have enough information to act, act. Do not re-derive facts already established… give a recommendation, not an exhaustive survey"* 로 강제한다. 스킬 인라인 제거.
- **Elicitation gate [Lens]**: 질문하기 전에 대화 이력·코드·합리적 기본값에서 스스로 답을 찾는다. **질문은 1개 지향, 3개 상한.** 하네스는 "루틴한 판단은 스스로"까지만 말하고 **개수 상한은 주지 않으므로** Lens 가 계속 책임진다.
- **승인은 전용 게이트 [Lens]**: 요구사항 질문은 승인 요청 전에 끝낸다. 승인 질문에 요구사항 질문을 섞지 않는다. 승인 게이트 자체가 Lens 구조물이라 비네이티브.

### F. 리서치 [Lens]

> 시스템 프롬프트에 리서치 규율은 없다. `WebSearch`/`WebFetch` 는 도구일 뿐 방법론을 강제하지 않으므로 이 절은 `/cr` 이 계속 책임진다.

- **Unrecognized Entity Rule**: 모르는 제품·릴리즈·대상은 답하기 전 무조건 검색한다. 판별 테스트: "답하려면 그게 뭔지 알아야 하는가?" 부분적으로 들어본 것은 지식이 아니다.
- **Effort scaling**: 단일 사실 1회 / 중간 난도 3~5회 / 심층 5~10회. 단일 검색으로 확정되면 1회로 끝낸다.
- **Snippet 불신**: 검색 스니펫만으로 단정하지 않는다 — 전문을 fetch 한다.
- **출처 위계**: 원출처 > 2차 출처. SEO 오염 영역(제품 추천 등)은 상위 랭크라도 회의적으로 본다. 충돌하는 출처는 충돌한다고 명기한다.
- **"없음" 과신 금지**: 검색 결과의 부재를 존재의 부재에 대한 증거로 단정하지 않는다.

### G. 공통 보고 [일부 네이티브]

> 시스템 프롬프트가 미사여구·사과·전문 나열을 이미 억제한다. 남는 Lens 몫은 **서브에이전트 → Leader 보고 형식**(Leader 가 파싱해야 하므로)과 **산출물 풀 경로**(사용자 강한 룰)다. 인-컨버세이션 보고는 호스트에 맡긴다.

- **결론 선행**: 첫 문장 = 무슨 일이 있었나 / 무엇을 발견했나.
- **가독성 > 간결성**: 짧게 만드는 방법은 항목의 선택적 포함이지, 단편·화살표 체인·전문용어 압축이 아니다. 완전한 문장으로 쓴다.
- **최종 메시지 완결성**: 사용자가 필요로 하는 전부(답·요약·결론·산출물 위치)는 마지막 메시지 안에 있어야 한다.
- **내부 기제 내레이션 금지**: "지침에 따라", "모듈을 로드했습니다" 류 셋업 서술 금지 — 결과만 말한다.
- **postamble 금지**: 산출물 링크 뒤에 긴 후기를 붙이지 않는다.

## 4. 충돌 심사 기록

Lens 기존 설계와 원문 원칙이 충돌해 보인 3건의 심사 결과. (4.1 은 v3.24.0 에서 재심사·개정, 4.2·4.3 은 Lens 설계 유지.)

### 4.1 모델 할당 테이블 vs 모델 오버라이드 절제

- 충돌: Lens 는 전 워커에 opus 를 고정 할당했다(/cc v3.11 설계). 원문 원칙은 모델 오버라이드를 절제하고 상속을 기본으로 한다.
- 구 해소(v3.23 이하): 품질 우선 케이스로 고정 할당 유지 + "불확실하면 상속" 보강.
- **재심사·개정 (v3.24.0, 2026-07-15 사용자 지시)**: 고정 이름 할당 **폐지** — "최고 모델 무차별 배정 금지, 업무 난이도에 맞춰 배분"이 원칙. 배분은 **난이도 사다리** — Easy=경량 티어(현재 haiku) / Medium=중간 티어(현재 sonnet) / Hard=**최상위 티어(TOP)**. 각 칸은 이름이 아니라 상대 위치라서 모델 세대와 함께 자동 상승한다.
- **재개정 (v3.25.0, 2026-07-20) — 상속 폐기 + 위험도 기반 승격**: v3.24 의 "세션이 enum 최상위 이상이면 지정 생략(상속)" 조항을 **폐지**한다.
  - **모든 spawn 은 모델을 명시한다.** TOP = Task enum 최상위 명시(현재 `fable`, 없으면 `opus`).
  - **폐지 사유 (실측 2026-07-20)**: ① 지정을 생략하면 추적 훅이 실제 모델을 관측할 수 없다(`tool_input.model` = undefined) — 계측 자체가 불가능해진다. ② 이 사용자의 세션은 항상 최상위 모델이라, 상속 조항이 **모든 Hard 역할을 자동으로 최상위로 만들었다.** 정책을 완벽히 지켜도 최상위 소비가 큰 구조였고, 이것이 최상위 티어 사용량 과다의 직접 원인이었다.
  - **원문 원칙과의 관계**: 원문은 "오버라이드 절제·상속 기본"을 권한다. 이번 개정은 그와 **의도적으로 갈라선다** — 관측 가능성과 비용 통제를 상속의 편의보다 우선한다. 감수한 대가: 세션이 enum 보다 새로운 모델일 때 한 단계 낮게 잡힐 수 있음(enum 자동 갱신으로 창은 좁다).
  - **Supervisor·QA**: "최고 사용 Worker 티어와 동급"(연쇄 승격) **폐지** → **위험도 기반**. 파괴적·비가역 변경 / 파일 5개+ 또는 diff 300줄+ / 보안·권한 경로일 때만 TOP. 리뷰 깊이가 필요한 것은 worker 가 똑똑했을 때가 아니라 **틀렸을 때 손해가 클 때**다.
  - **TOP 상한 (명령 1회 기준)**: `/cc` 3 · `/cp deep` 2. 초과 필요 시 사유와 함께 사용자 확인. (`/ccp` 1 은 v3.29 스킬 폐지로 소멸.)
  - ~~Monitor 는 `haiku` 고정~~ → **v3.29 에서 Monitor 역할 자체를 폐지.** 모델 배정 대상이 아니다(§4.6).
- **보강 (v3.37.0, 2026-09-04 사용자 지시) — 계획 작성은 사다리의 Critical 칸이다.** 지시 원문: *"기획을 할 때는 왠만하면 fable 5.1 을 쓰게 해. 계획서를 쓸 때는 특히."* 사다리를 계획 활동 자체에 적용하면 결론은 하나다 — 계획서는 **되돌리기 어려운 결정을 문서에 박는 활동**이고, 여기서 틀리면 실행 워커 전원이 틀린 것을 정확하게 만든다. 워커에는 TOP 을 쓰면서 워커가 따를 계획은 세션 기본 모델로 쓰는 것은 사다리를 거꾸로 세운 것이다.
  - 세션이 **이미 TOP** 이면 세션 안에서 쓴다 — **spawn 하지 않는다.** 부모가 대화·조사 컨텍스트를 갖고 있어 위임이 순손실인 것은 Pre-mortem 3.1 판정과 같다.
  - 세션이 **TOP 미만**이면 `/cp` Phase 1~2.5 를 `Agent(model: "fable")` 로 위임하되 **컨텍스트 전량**(원본 요청·What/Why·조사 산출·인벤토리)을 실어 보낸다. 컨텍스트 없는 위임은 상위 모델이 아니라 무지한 모델을 쓰는 것이다.
  - 이 위임은 **1 spawn** 이며 §4.1 의 TOP 상한(`/cc` 3 · `/cp deep` 2) 안에서 소비된다. 상한을 늘리지 않는다.
  - 어느 쪽이든 계획서 frontmatter `planner_model:` 에 기록한다 — 기록이 없으면 `/crv` 가 사후에 무엇으로 썼는지 알 수 없고, 상속 폐기(v3.25)가 없애려던 계측 구멍이 계획 축에 그대로 남는다.

### 4.2 AskUserQuestion 승인 게이트 vs 되묻기 차단

- 충돌: Lens 는 승인 게이트에서 AskUserQuestion 으로 사용자에게 묻는다. 원문 원칙은 작업 중 되묻기를 차단한다.
- 해소: 승인 게이트는 파괴적 행동·스코프 결정에 대한 질문이므로 원문이 허용하는 예외에 해당한다 — **유지**. 차단 대상은 작업 중간의 "~할까요?" 류 허락 구하기뿐이다.

### 4.3 2분 진행보고 vs 푸시 알림 절제

- 충돌: Lens 는 2분 주기 진행보고를 한다. 원문 원칙은 푸시 알림을 절제하라고 한다.
- 해소: 진행보고는 대화 안의 텍스트 한 줄이므로 충돌이 아니다 — **유지**. 사용자 주의를 강제로 끄는 푸시 알림과는 구분한다.

### 4.4 진행보고 규약 (SoT · 주기 2분 · 훅으로 강제 · v3.29 수행 주체 변경)

> 이 절이 진행보고의 원본이다. 각 스킬은 런타임에 자기 SKILL.md 만 읽으므로 **동일 취지를 스킬마다 인라인**으로 복제한다(include 불가 — 확립된 제약).
>
> **v3.29: 규칙은 유지, 수행 주체만 바뀐다.** 종전에는 전담 Monitor 서브에이전트(haiku)를 매 실행마다 띄워 폴링시켰다. 지금은 **스킬 본체(Leader)가 직접** 보고한다 — 하네스가 백그라운드 작업 완료 시 본체를 자동 재호출하므로 폴링 에이전트는 순수 오버헤드다. 상세 근거는 §4.6.

**발동 조건**: 백그라운드/장시간 작업이 **2분 이상** 걸리는 모든 구간. 대상에는 Task 서브에이전트, **Workflow**, codex 호출, 장시간 Bash 가 전부 포함된다. (v3.16 원규칙은 Workflow 도구 이전에 작성되어 이를 누락했다 — 이번에 포함.)

**주기 = 2분 = 120초** (사용자 지시 — "cc 할 때 반드시 2분마다 진행사항 보고"). v3.16 이 주기를 120초 → 300초 로 완화했던 것을 되돌린다. 사용자 기존 룰(`feedback_wait_progress_report`)이 원래 120초였으므로 완화 자체가 회귀였다.

**매 보고에 반드시 들어갈 것 (세 가지 전부, 하나라도 빠지면 위반)**:

1. **생존 확인 결과** — 추측 금지. `TaskOutput(block=false)` 또는 산출 디렉토리 mtime 으로 **실제로 확인한 뒤** 보고한다. **확인하지 않은 채 "진행 중"이라고 말하지 않는다.**
2. **끝난 것 / 남은 것** — N/M 형태로. 무엇이 완료됐고 무엇을 기다리는지.
3. **부분 산출물** — 지금 낼 수 있는 결과(초안·확정된 결정·부분 설계)가 있으면 대기 중이라도 **먼저 낸다.** 대기가 산출물을 100% 막지 않게 한다.

**금지**: "아직입니다" / "진행 중입니다" 만 적는 보고. 정보량 0 이며 규칙 위반이다.

**강제 수단 = 훅** (산문 규칙만으로는 조용히 스킵된다 — 실측):

- 구현: `hooks/post-tool-progress.js`, `PostToolUse`(matcher 없음 = 전 도구)에 등록. 상태 파일 `.lens/progress-report-state.json`.
- 동작: 도구 호출마다 경과를 확인하고 **마지막 보고 기점 이후 120초를 넘겼으면** 보고를 요구하는 리마인더를 `additionalContext` 로 주입한다. 리마인더에는 위 세 요소와 "'아직입니다'만 적는 보고는 위반"이 그대로 박혀 있다.
- **오탐 억제**: 백그라운드 작업이 실제로 in-flight 일 때만 울린다. 판정 = ① `run_in_background:true` **또는** ② `Task`/`Agent` 반환의 async-launch **봉투**(§4.7 과 동일 판별) **또는** ③ `Workflow` 반환의 **Workflow 전용 봉투** **또는** ④ 폴링 도구(`TaskOutput`/`BashOutput`/`SendMessage`/`KillShell`/`KillTask`/`TaskStop`) 를, **최근 180초 내에** 본 경우. 백그라운드 작업이 없는 짧은 대화 턴에서는 무장되지 않아 침묵한다.
  - ①은 **도구 이름 게이팅이 없다** — 백그라운드 `Bash` 가 여기서 잡힌다. `Bash` 는 백그라운드여도 결과의 `stdout` 이 비어 오므로 **텍스트 매칭을 쓰면 안 된다**(실측: 그 런치 문구를 `grep` 한 명령의 출력이 스스로를 무장시킨다).
  - **`Workflow` 는 별도 봉투를 쓴다.** `run_in_background` 필드가 없고 반환에 agent 문구(`Async agent launched` / `working in the background`)가 **하나도 없어** agent 봉투로는 영원히 무장되지 않는다. 실측(2026-07-25, 4개 세션 25건) 봉투는 텍스트 `Workflow launched in background. Task ID: <id> … Run ID: wf_<id>` 또는 구조화 결과 `{status:'async_launched', taskId, runId, taskType}` 이며, 어느 쪽이 `tool_response` 로 오는지 미확정이라 **두 철자를 모두 받되 마커·식별자를 함께 요구**한다. 25건 중 1건은 권한 거부로 **아예 뜨지 못한 런치**였고 마커·식별자 어느 쪽도 없어 정상 탈락한다 — 마커 단독 판정을 쓰지 않는 이유다.
- **TTL(180초) 초과는 해제가 아니라 휴면이다.** 상태를 버리지 않는다. 평범한 도구는 휴면 상태를 보지 못하므로 여전히 침묵한다(오탐 억제 유지). **늦은 신호가 보고 시계를 리셋하지 않는다** — 예전에는 TTL 초과 폴링이 상태를 새로 만들며 `lastReportAt = now` 로 리셋해서, **180초보다 긴 간격으로 폴링하면 2분 규칙을 무한 회피**할 수 있었다(Codex 7차 P2, 실측 재현: 4회 반복에 리마인더 0회).
- **연속성 판정**: 휴면 상태에 신호가 왔을 때 직전 신호와의 간격이 **360초(보고 주기 ×3)** 이내면 같은 폴링 루프로 보고 즉시 판정한다. 그보다 길면 그 1회는 침묵하되 마커를 남기고 **다음 신호에서 판정**한다 — "끝난 작업의 마지막 수거 호출" 과 "느린 폴링" 은 그 순간의 도구 스트림상 **구분이 불가능**하기 때문이다(구분할 만한 두 소스는 이미 봉쇄돼 있다: 폴링 응답 형태는 미실측이라 배선 금지 §4.7, 대시보드는 신뢰 불가). 그래서 시간에 걸친 **거동**으로 가른다 — 살아있는 작업은 신호를 계속 내고, 끝난 작업은 한 번 내고 멈춘다.
- 결과적으로 **어떤 폴링 간격에서도 회피는 최대 1회**다.
- **도구 이름만으로는 무장하지 않는다** (Codex 3차 리뷰 P2, 실측 재현): **전경** `Task`/`Agent` 는 `PostToolUse` 시점에 **이미 완료돼 있다** — 이 훅은 서브에이전트가 끝난 뒤에야 돈다. 그래서 이름만 보고 무장하면 진행 중 작업이 0인데도 120~180초 뒤 아무 평범한 도구에서 "백그라운드 작업 대기 중" 리마인더가 발화한다. `run_in_background === false` 는 **조기 거부**한다(전경 선언). 이름 게이팅 자체는 유지한다 — 없애면 이 문서를 `Read` 하는 것만으로 async-launch 문구가 매칭돼 새 오탐이 생긴다(훅을 주제로 작업하는 에이전트가 자기 보고문으로 자기를 무장시키는 경로).
- **§4.7 과 판별을 공유한다**: 두 훅이 같은 두 신호(`run_in_background` 플래그 / 반환 텍스트 문구)를 쓴다. 하네스가 그 문구나 파라미터를 바꾸면 `post-tool-task.js` 의 거짓 `done` 재발과 이 훅의 무장 실패가 **동시에** 나타난다 — 단일 감시 지점으로 취급하라.
- **`.lens/agent-dashboard.json` 을 in-flight 근거로 쓰지 않는 이유**: 그 데이터는 이 목적에 신뢰할 수 없다. `PostToolUse` 는 async spawn 직후(~130ms)에 발생하므로 트래커가 백그라운드 에이전트를 즉시 `done` 으로 찍었다(실측 2026-07-25 — 10개 전원 배포 직후 `done`, 그중 둘은 이후 311초·567초 실행). fan-out 직후 "0 running" 을 읽으면 훅이 영구히 침묵한다. 그래서 훅은 도구 호출 스트림을 **직접** 관측한다. (거짓 `done` 자체는 `hooks/post-tool-task.js` 에서 수정 — 아래 §4.7.)
- **봉투는 두 철자로 온다 — 둘 다 받는다** (Codex 11차 후속, 실측 2026-07-26). 같은 async 런치가 산문 봉투(`Async agent launched …` + `agentId:`/`output_file:`)로도, **구조화 결과**(`{status:'async_launched', isAsync:true, agentId, outputFile, …}`)로도 온다 — 한 세션의 async Agent 런치 **41건 전부**가 후자였다. 산문 철자만 요구하면 그 payload 에는 문장이 아예 없어 봉투가 영영 성립하지 않고, **§4.4 강제와 §4.7 계측이 동시에 죽는다.**
  - ⚠️ **`tool_response` 가 content-block 배열이면 `JSON.stringify` 로 검색하지 마라.** 그러면 개행이 `\` 와 `n` 두 글자로 escape 되어 `agentId:` 앞에 **단어 문자**가 오고, `\bagentId:` 의 단어경계가 깨져 식별자가 안 잡힌다(문장은 잡히는데 식별자만 빠져 봉투가 조용히 실패한다). 배열은 **`.text` 를 펼쳐서** 검색한다. 두 훅의 `responseText()` 가 같이 이 처리를 한다.
- **턴이 끝나면(`Stop` 훅) 상태 파일을 지우지 않고 `lastReportAt` 을 스탬프한다.** 사용자가 방금 메시지를 받았으므로 시계는 리셋되지만, **삭제하면 그 타임스탬프가 사라져** 다음 폴이 새 시계로 재무장하고 리마인더가 2분 더 밀린다 — 위에서 막은 "늦은 신호가 시계를 리셋" 회피와 같은 경로다. 무장 필드는 건드리지 않는다.
- **세션 경계(`SessionStart`)에서는 상태 파일을 삭제한다 — 단 소스가 `startup`·`resume`·`clear` 일 때만.** 상태에는 시계(`armedAt`/`lastSignalAt`/`lastReportAt`/`reminders`)만 있고 **작업 식별자가 없으므로** 지워도 떠 있는 작업을 놓치지 않는다. 애초에 이전 세션의 백그라운드는 새 CLI 프로세스에서 무장 신호(프로세스가 소유한 핸들)를 낼 수 없다. 남겨두면 새 세션의 **첫 폴링이 즉시 발화하며 "대기 7201초째" 같은 거짓 경과**를 보고한다(실측 재현).
  - **`compact`·`fork`·알 수 없는 소스에서는 지우지 않는다.** 둘 다 대화 **도중** 발화하고(긴 대기 중 auto-compact, 에이전트가 띄우는 `fork`) 같은 상태 파일을 공유하므로, 거기서 지우면 `Stop` 이 스탬프로 막았던 회피가 그대로 재생된다. **허용목록**으로 판정한다 — 보존의 최악은 시끄러움, 삭제의 최악은 침묵이고 침묵이 더 나쁘다.
  - 기준선: `Stop`(에이전트가 유발하는 턴 주기) = **스탬프**, `SessionStart` 중 사용자 행동(`startup`/`resume`/`clear`) = **삭제**.
  - ⚠️ `hooks/hooks.json` 의 `"once": true` 는 매처 **그룹** 레벨에 있어 하네스가 무시한다(스키마상 `once` 는 hook 엔트리 필드 — claude 바이너리 실측). SessionStart 훅은 **모든** SessionStart 이벤트(`startup|resume|clear|compact|fork`)에서 실행된다고 전제해야 한다.
- 한계: **블로킹 도구 호출 도중에는 PostToolUse 가 발생하지 않아** 주입이 불가능하다. 장시간 작업은 백그라운드 spawn + 폴링 형태로 돌려야 훅의 보호를 받는다.
- 실패해도 세션을 깨뜨리지 않는다(`installFailSoftHandlers` + 락 실패 시 무락 폴백).
- **`ScheduleWakeup` 을 강제 수단으로 쓰지 않는다** — `/loop` 전용 페이서이고 스키마가 "백그라운드 폴링용 짧은 주기 예약 금지 / 최소 60초 클램프"를 명시한다. 훅이 유일한 실제 강제 수단이다.

**위반 판정 기준** (하나라도 해당하면 위반):

1. 120초를 넘겨 보고가 없었다 (훅 리마인더가 떴는데도 무응답이면 명백한 위반).
2. 생존확인 **실측 없이** "진행 중"이라고 썼다.
3. 세 요소 중 하나라도 빠졌다 (특히 ③ 부분 산출물 — 낼 수 있는데 안 냈다).
4. 정보량 0 인 보고("아직입니다")로 주기만 채웠다.

**유실·정지 감지 시**: 즉시 사용자에게 보고하고, **복구보다 폐기·재판단을 우선 검토**한다. 죽은 작업을 계속 기다리지 않는다.

**근거 (실측 사고 2026-07-20)**: Workflow 가 조용히 사망(`journal.jsonl` 미생성 · 태스크 레지스트리 부재 · 완료 알림 없음)했는데 생존 확인 없이 "진행 중"을 2회 오보하고 사용자를 여러 턴 대기시킴. 사용자 지적: *"지금 이렇게 기다릴때 나는 답답해"* → *"대기를 없앨수는 없고, 진행 현황을 알려주면 되지. 주기적으로."*

### 4.5 Karpathy Rule 1 vs 하네스 되묻기 정책 (v3.29 신설)

- **충돌**: 사용자 전역 지침의 Rule 1(Think Before Coding)은 *"불확실하면 묻는다 / 해석이 여러 개면 모두 제시한다 / 불명확하면 멈춘다"* 를 요구한다. 현재 하네스는 반대 방향을 요구한다 — *"Interpret ambiguity the way a careful colleague would: make routine judgment calls yourself, and check in only when different readings would lead to materially different work"*, *"Reserve blocking questions"*, *"When you have enough information to act, act"*.
- **왜 지금 문제가 됐나**: Rule 1 전문이 스킬 본문 12곳에 복붙돼 있었다. 하네스는 한 번 말하는데 Lens 가 반대 취지를 열두 번 반복하면 **가중치가 Lens 쪽으로 기운다.** 사용자의 다른 룰(`feedback_try_first` — "해봐 하면 추측·옵션나열 금지, 즉시 실행")과도 어긋나 있었다.
- **판정 — 하네스 우선, 단 Rule 1 의 산출물 요구는 유지**:
  - **묻는 행위**는 억제한다. 질문은 1개 지향·3개 상한(§E Elicitation gate), 그 외 불확실성은 **묻지 말고 기록**한다.
  - **가정을 드러내라는 Rule 1 의 핵심**은 살린다 — 다만 대화 중 질문이 아니라 **계획서의 `가정`·`❓ 미해결 질문` 섹션**으로 배출한다. Rule 1 이 막으려던 것은 "혼란을 숨기는 것"이지 "스스로 판단하는 것"이 아니다.
  - **"불명확하면 멈춘다"** 는 파괴적·비가역 작업에만 적용한다. 가역적 작업에서 멈추는 것은 하네스·사용자 룰 양쪽 위반이다.
- **적용 위치**: `/cp` 본문에 이 판정을 인라인 1블록(비네이티브 — 하네스는 질문 개수 상한을 주지 않음). `/cc` 워커 프롬프트의 Rule 1 은 그대로 두되, 워커는 애초에 "멈추지 말고 끝내라" 계약이 함께 걸려 있어 상충하지 않는다.

### 4.7 백그라운드 spawn 은 완료가 아니다 (계측 규약)

**실측 결함 (2026-07-25)**: `Agent` 도구로 백그라운드 워커 10개를 배포한 **직후**, `hooks/post-tool-task.js` 가 전원에 대해 `done` 을 찍고 `All N agents complete` 를 출력했다. 실제로는 그 뒤 수 분간 돌았다(한 에이전트 311초, 다른 하나 567초). 원인: `PostToolUse` 는 **spawn 호출이 반환되는 순간** 발생하고, 훅이 `hasError ? 'error' : 'done'` 으로 무조건 완료 처리했다. 보고된 `132ms` 는 에이전트 수명이 아니라 spawn 호출 자체의 소요였다.

**판정 근거 (2가지 독립 신호 — 실측 확인)**:

1. `tool_input.run_in_background === true` (배포 10건 전부 존재).
2. 도구 반환 텍스트 — `Async agent launched successfully.` + `agentId: …` + `output_file: …` + "The agent is working in the background. You will be notified automatically when it completes."

**규약**:

- 백그라운드 launch 는 `done` 으로 마킹하지 않는다. **`launched`(완료 미관측)** 로 마킹하고 완료 집계에서 빼며, 훅 출력에 **"상태 미확정(done 아님)"** 을 드러낸다. 거짓 완료보다 미확정이 낫다 — 조용한 오보 금지.
- **`launched` 는 성공도 실패도 아니다.** `endSession()` 의 고아 스윕(`running`/`pending` → `error`)에서 **제외**된다. 관측하지 못한 것은 실패가 아니기 때문이다. `running` 으로 남기면 `Stop` 훅이 **매 턴** 발화하므로 수 초 안에 거짓 `error` 가 된다(실측) — 거짓 `done` 을 고치다 거짓 `error` 를 만드는 함정이다.
- `launched` 가 하나라도 있으면 **`All N agents complete` 류 문구를 출력하지 않는다.** 그 문구는 `running == 0 && launched == 0` 일 때만 참이다.
- 완료 판정은 **완료 알림 또는 산출물 실측**으로만 한다. 스킬·Supervisor 는 훅의 `done` 카운트를 완료의 증거로 쓰기 전에 실측을 요구하고, **`launched` 를 in-flight 판정 근거로도 쓰지 않는다**(정의상 "모름"이라 아무것도 해제하지 못해 리마인더가 영구히 울린다). 진행보고 훅은 그래서 대시보드가 아니라 **도구 호출 스트림을 직접 관측**한다.
- **완료 관측 경로 (조사 결론, 2026-07-25)**: `PostToolUse` 는 spawn 반환 시점에 **한 번만** 발화하므로 훅으로 완료를 볼 수 없다(실측: 220초 돌아간 에이전트에 두 번째 발화 없음). 하네스 이벤트 목록에 `SubagentStop`/`TaskCompleted`/`Notification:agent_completed` 가 존재하지만 **백그라운드 발화 여부·입력 스키마·상관 식별자가 문서화돼 있지 않아** 실측 프로빙 없이 배선할 수 없다. `launched` 는 그 배선이 생기면 `completeAgent(agentId,'done')` 으로 그대로 해소되는 **전방 호환** 상태다.

### 4.8 계획서 "표시"는 산출물이 아니라 행위다 (v3.37)

**사용자 지적 (2026-09-04)**: *"board 및 md파일 뭐 저장은 한대. 근데 저장했으니, 승인해라 이렇게만 보고를 해 … 맨날 계획서 찾는다고 탐색기 찾고 뭐하고 아주 지겨워 죽겠어."*

§6 의 판정 규칙 — *"눈에 보이는 산출물은 산문 지시로도 이행된다. 코드 게이트는 눈에 안 보이는 자기절제에만 필요하다"* — 을 이 건에 그대로 적용하면 왜 산문이 졌는지가 나온다.

- **산출물은 실제로 만들어졌다.** `docs/tasks/{id}.md` · `.html` · `docs/board_*.html` 은 산문 지시만으로 18개 레포에 생성됐다(§6 실측). 파일은 만들면 눈에 보인다 — 모델 자신의 출력에 남으므로 누락이 즉시 드러난다.
- **띄우는 것은 산출물이 아니라 행위다.** 브라우저를 여는 일은 **모델의 출력에 아무 흔적도 남기지 않는다.** 안 해도 대화만 보면 티가 안 나고, 대신 **사용자가 탐색기를 뒤지는 비용으로 청구된다.** "산출물 링크는 풀 경로" 라는 산문 규칙이 v3.25 부터 있었는데도 같은 불만이 2026-09-04 에 나온 이유다.
- **처방**: 행위를 **기록**으로 바꿔 산출물의 성질을 부여한다. `scripts/show-report.js` 가 열고 `.lens/report-shown.json` 에 `{method, file|url, shownAt}` 을 남기며, `/cp` Phase 5.0 §7 게이트가 그 기록을 읽는다. 기록이 `browser`·`artifact` 가 아니면 승인 요청 자체가 막힌다.
- **실측 함정 (2026-09-04, v3.37.1 에서 수정)**: Windows 에서 `.md` 는 연결 프로그램이 없을 수 있다(`assoc .md` → exit 1, `FileExts\.md\UserChoice` 키 없음). 그때 `cmd /c start "" file.md` 는 **exit 0 을 내면서 창도 다운로드도 만들지 않는다** — `file://` URL 로 바꿔도 같다. 종료 코드만 믿으면 **"띄웠다"가 기록되고 게이트가 통과되는데 화면에는 아무것도 없다.** 그래서 ① win32 는 확장자 연결을 먼저 확인하고 ② 덱이 없는 계획은 `.lens/preview/{id}.html` 로 감싸서 연다. 창 제목 실측으로 확인 — 프리뷰 도입 전 `chrome` 제목 무변화, 도입 후 계획 id 로 변경.
- **정직성 조항**: SSH·헤드리스 세션에서 원격 기계의 브라우저를 여는 것은 **아무도 안 보는 창을 띄우는 것**이다. 그런 세션은 `remote` 로 기록하고 게이트를 통과시키지 않는다 — Artifact 로 발행해 URL 을 되먹이거나, **띄우기 실패를 승인 화면 첫 줄에 적는다.** 조용한 성공 주장이 이 규칙이 없애려는 실패 모드 그 자체다.
